# 群龙详细设计 03:能力声明与感知派单

> 状态:**初稿,供评审**。
> 本文承接纪要 §8 第 3 项。能力声明是整个分布式系统的"搜索索引"(派单决策本质是一次查询),但它**只提供决策输入,不替任何节点做决策**——排序与取舍永远在牵头方(纪要"中心做服务,边缘做决策")。
> 依赖:01 篇的 `required_caps` / `reject(unsupported_caps)` / R6;02 篇的 Node 表(`caps_rev`/`load` 字段)与 `/v1/teams/{id}/nodes` API。

## 1. 范围

**本文确定:** 能力标签模型与命名、匹配语义、静态与动态档案的划分、上报协议、牵头方查询协议、执行方自评语义(接单五道闸)、**远端任务执行档案**(§6.1,全系统"远端执行权"的第一份设计归属)、失败回流的反馈闭环。

**本文不定:** 能力的实测验证(probe)、跨团队能力共享、基于负载的调度策略(那是牵头方的智能,不在协议里)。

## 2. 设计原则(编号接续 P13+)

- **P13 能力是声明,不是承诺**。档案用于缩小候选集;真正的闸门是执行方接单时的自评与拒绝(01 R6 NACK 优先)。声明可以过期、可以不准,拒绝不会。
- **P14 注册中心存档案、不做决策**。查询语义 = 过滤;返回结果不给排序、不打分(笨中心,P11 的延续)。
- **P15 静态与动态分离**。环境/工具/硬件是慢变量(变更时上报);负载/在线是快变量(周期刷新 + 短 TTL)。两者的时效语义不同,混在一起必然要么过时要么风暴。
- **P16 过期按未知,不按满**。动态档案过期后视为"信息缺失",候选照常返回(牵头方自行权衡);绝不因档案过期自动把节点判为不可用——那会把时钟问题变成可用性雪崩。

## 3. 能力模型 v1:标签 + 负载

### 3.1 静态能力:扁平标签

标签形态 `类:值[@版本]`,五个初始类:

| 类 | 含义 | 示例 |
|----|------|------|
| `env` | 操作系统与运行时环境 | `env:windows`、`env:wsl2`、`env:python@3.12` |
| `tool` | 工具链 | `tool:docker`、`tool:node@20`、`tool:ios-sign`(团队内约定的组合能力) |
| `hw` | 硬件资源 | `hw:gpu-cuda`、`hw:ram-64g` |
| `net` | 网络位置 | `net:office-vpn`(能摸到内网资源) |
| `ext` | 已接入的外部账号/服务 | `ext:github-org-acme` |

规则:

- 值小写;未知类**照存照传**(向前兼容,接收方不认识的类不参与匹配但不报错);
- 组合能力(如 iOS 签名 = 环境 + 证书 + 工具)允许封装成单个团队约定标签,不必拆解——标签是给人及其"龙"约定的词汇表,注册中心不做语义校验;
- 负标签不做(声明"没有 X"是无穷集合)。

### 3.2 匹配语义

| offer.required_caps 写法 | 节点档案 | 匹配 |
|--------------------------|----------|------|
| `tool:node` | `tool:node@20` | ✅(无版本要求 = 存在即可) |
| `tool:node@20` | `tool:node@20` | ✅(精确) |
| `tool:node@20` | `tool:node@18` | ❌(大版本不满足) |
| `env:ios-sign` | `env:ios-sign` | ✅ |

规则:无 `@` = 前缀匹配(存在该能力即可);带 `@` = 精确到所写版本段。v1 不做区间语法(`@>=18` 留给后续,需求出现再加)。

### 3.3 动态档案:负载

| 字段 | 说明 |
|------|------|
| `queue_depth` | 本地待办任务数(含已接受的远端任务) |
| `running` | 正在执行的任务数 |
| `accepting` | 布尔:当前是否愿意接新单(执行方自己的策略开关,如夜间不接) |
| `ts` / `ttl_ms` | 快照时刻与有效期(默认 60s) |

`accepting=false` 是**礼貌提示而非闸门**:offer 仍可送达(离线暂存同款语义),执行方是否拒绝由它自己当场决定——与 P13 一致,负载信息只影响牵头方的候选排序,不构成协议层拒绝。

## 4. 上报协议

- **全量上报**:enroll 时(02 §4)与 `PATCH /v1/nodes/me` 时携带完整静态标签集 + 负载快照;注册中心整体替换,`caps_rev` 自增(目录查询用 rev 判断新旧)。
- **静态变更**(装了新工具、换了环境):检测到即上报,无周期。
- **动态刷新**:默认 60s 周期随 `PATCH` 上报;`accepting` 翻转、任务大进大出时立即上报(事件触发 + 周期兜底)。
- 上报走注册中心 HTTP,**不进 task.* 消息**——保持任务信封瘦身,也让"不上报负载"的老节点天然兼容(只是动态信息缺失)。

## 5. 查询协议(牵头方视角)

```
GET /v1/teams/{id}/nodes?caps=env:ios-sign,tool:node@20&online=true
→ 200 [{node_id, name, online, caps:[…], load:{…, ts, ttl_ms}, caps_rev}]
```

- 过滤条件全匹配(caps 为 AND);`online=false` 的节点也返回(带最后档案),由牵头方决定要不要对离线候选发暂存单。
- 动态档案过期(§3.3 TTL)时该字段返回 `null` + 节点照常在列(P16)。
- **返回按 node_id 稳定排序,无评分**。负载加权、信任加权、往返成本(刚协作过的节点更熟)——全是牵头方本地策略,协议不背(✅ P14)。

兜底通道:目录查询不到时,牵头方可以对疑似候选发 `rpc.ask`(01 §4.1)口头询问"你有没有 X"——互助场景的即兴能力发现,不进注册中心。注册中心是索引,rpc.ask 是询问,两者并存。

## 6. 执行方自评(接单五道闸)

offer 到达后按序评估,任一不过 → 立即 `reject`(01 R6,禁止沉默):

| 闸 | 检查 | 拒绝码 |
|----|------|--------|
| 1 签名 | 验签(01 §3.3,task.* 与 rpc.* 均必签) | 丢弃,不回声 |
| 2 策略 | team 复核(02 A5)、本地策略(如夜间免打扰) | `policy_denied` |
| 3 能力 | `required_caps` 逐条按 §3.2 匹配 | `unsupported_caps` |
| 4 负载 | `queue_depth`/`running` 超过本地阈值、或与已有任务资源冲突 | `busy`(`retry_after_ms` 可选) |
| 5 执行档案 | 任务所需权限(`requires` 声明,01 §4.2)超出远端执行档案默认(§6.1)→ 按节点策略拒绝,或转本地人确认后放行 | `policy_denied`(或确认后放行) |

闸 3 拒绝时,`reject.detail` 附 `missing:[…]`(缺哪几条)。这同时关闭了 01 篇开放问题 5:拒绝回执即反哺——牵头方拿到 missing 明细,改派时可精确排除并更新本地"节点-能力"记忆,不必全网重查。

### 6.1 远端任务执行档案(remote task profile)

**这是全系统最锋利的面,本文认领它**:执行方的"龙"将以本地真实权限,运行一条由牵头方 LLM 写成的任务书——不需要任何人被攻陷,一条写歪或被上游注入的 `summary` 就足以让队友机器做危险动作。"提示注入"在这里不是攻击者的技巧,而是常规路径的固有属性。因此:**一切远端来源的任务(kind=aid 与 kind=project 一律)默认套用低于本地任务的执行档案**;本机用户发起的本地任务不受影响。

| 维度 | 本地任务 | 远端任务默认 |
|------|----------|--------------|
| 工作区 | 用户授权范围 | 仅 `offer.workspace` 指定的目录(选型见纪要 §8.4),越界拒绝 |
| 工具 | 全部已装 | 节点策略白名单内 |
| 网络出口 | 不限 | 受限出口(白名单/代理),默认拒绝内网敏感网段 |
| 凭证 | 环境内全部 | 不注入节点持有的敏感凭证(SSH key、API token、证书) |
| 敏感操作 | 自行执行 | 大范围删除、系统级安装、读取凭证等 → 需本地人确认 |

- 档案是**执行方本地策略**(配置预设);offer 只能*声明*需要什么(`requires` 字段),永远不能*放宽*档案——权限的收窄权始终在执行方(P13 的延伸)。
- 档案缩窄的是**爆炸半径**,不承诺消除提示注入;残余风险由"敏感操作本地人确认"兜底——文档如实声明,不假装这是一个已被解决的问题。

## 7. 反馈闭环

派单系统的能力档案必然漂移(声明有、实际没有;或反过来)。v1 用最小闭环修正,不建主动探测:

```
task.fail(env_missing) —— fail body 增加可选 missing_caps[]
        │
牵头方:更新本地节点-能力记忆(降权/拉黑该标签),改派时排除
        │
(节点侧)重复失败 → 本地自动摘除该标签并重新上报(自愈)
```

- `task.fail` 的 body 增加**可选**字段 `missing_caps[]`(01 §4.2 的 body 概要在此细化,不破坏 v1 兼容——新增可选字段)。
- 节点侧自愈:同一标签被多次 `env_missing` 命中(阈值本地定),群龙自动把该标签从静态档案摘除并触发上报——声明与现实对齐,无需人工。
- 主动探测(派发轻量 probe 任务实测能力)明确**不做**:成本高、且 NACK/失败回流已覆盖主要漂移场景。留给未来按需评估。

## 8. 隐私边界

能力档案是机器画像(暴露"这台机器有什么、缺什么"),可见范围 = **本 team**(02 的目录查询本就 team 鉴权)。跨 team 不可见,v1 无例外;未来跨团队 grant(02 §12.1)生效时,能力可见性必须作为 grant 的显式选项,不默认开放。

## 9. 决策记录(接续 D13–D17)

| # | 决策 | 结论 |
|---|------|------|
| D18 | 模型 | 静态 = `类:值[@版本]` 扁平标签,未知类照传;动态 = 负载快照 + TTL;匹配 = 无版本前缀 / 有版本精确 |
| D19 | 时效 | 静态变更即报;动态 60s 周期 + 事件触发;过期按未知处理,不按满(P16) |
| D20 | 职责 | 注册中心只过滤不排序;负载影响候选排序不构成协议层拒绝;最终闸门是执行方五道自评 |
| D21 | 修正 | 失败回流(可选 `missing_caps[]`)+ 节点侧自愈摘标签;不做主动探测 |
| D22 | 执行权 | 远端任务默认套用低权执行档案(工作区/工具/网络/凭证/敏感操作确认);offer 可声明 `requires` 但不可放宽档案;档案缩窄爆炸半径,本地人确认兜底残余风险 |

## 10. 开放问题

1. **版本区间与组合匹配**:`@>=18`、`hw:ram>=32g` 这类谓词语法,等真实派单需求出现再定。
2. **能力实测(probe)**:高价值标签(如 ios-sign)的注册时校验任务。
3. **负载之外的因素**:时区/时段偏好、电量(移动设备)、计费——先把 `accepting` 开关跑起来,策略复杂化前不改协议。
4. **跨团队能力可见性**:与 02 §12.1 的 grant 模型联动设计。
