# 群龙详细设计 03:能力声明与感知派单

> 状态:**v2,已整合评审委员会修订**(行内以「评审 I-xx」标注来源,见 `QUNLONG_DESIGN_REVIEW_REPORT.md`)。
> 本文承接纪要 §8 第 3 项。能力声明是整个分布式系统的"搜索索引"(派单决策本质是一次查询),但它**只提供决策输入,不替任何节点做决策**——排序与取舍永远在牵头方。
> 依赖:01 篇的 `required_caps` / `requires` / `reject(unsupported_caps)` / R6/R8/R10;02 篇的 Node 表(`caps_rev`/`load`)与 API 面。

## 1. 范围

**本文确定:** 能力标签模型与命名(含值字符集)、**匹配语义定案**(§3.2)、静态与动态档案的划分与时效基准、上报协议、牵头方查询协议、执行方自评语义(接单五道闸)、**远端任务执行档案**(§6.1)、**requires 与本地确认契约**(§6.2)、**同队执行面缓冲带**(§6.3)、**两段式能力自愈**(§7)、档案隐私与留存。

**本文不定:** 能力的实测验证(probe)、跨团队能力共享、基于负载的调度策略(牵头方的智能,不在协议里)。

## 2. 设计原则(编号接续 P13+)

- **P13 能力是声明,不是承诺**。档案用于缩小候选集;真正的闸门是执行方接单时的自评与拒绝(01 R6 NACK 优先)。声明可以过期、可以不准,拒绝不会。
- **P14 注册中心存档案、不做决策**。查询语义 = 过滤;返回结果不给排序、不打分(笨中心,P11 的延续)。
- **P15 静态与动态分离**。环境/工具/硬件是慢变量(变更时上报);负载/在线是快变量(周期刷新 + 短 TTL)。时效语义不同,混在一起必然要么过时要么风暴。
- **P16 过期按未知,不按满**。动态档案过期后视为"信息缺失",候选照常返回(牵头方自行权衡);绝不因档案过期自动把节点判为不可用——那会把时钟问题变成可用性雪崩。

## 3. 能力模型 v1:标签 + 负载

### 3.1 静态能力:扁平标签

标签形态 `类:值[@版本]`,五个初始类:

| 类 | 含义 | 示例 |
|----|------|------|
| `env` | 操作系统与运行时环境 | `env:windows`、`env:wsl2`、`env:python@3.12` |
| `tool` | 工具链与**组合能力** | `tool:docker`、`tool:node@20`、`tool:ios-sign`(环境 + 证书 + 工具的团队约定封装) |
| `hw` | 硬件资源 | `hw:gpu-cuda`、`hw:ram-64g` |
| `net` | 网络位置 | `net:office-vpn`(能摸到内网资源) |
| `ext` | 已接入的外部账号/服务 | `ext:github-org-acme` |

规则:

- **值字符集**:`[a-z0-9]` 加 `-` / `_` / `.`;`:` 与 `@` 为结构保留字,值内不得出现(评审 I-30③);
- **未知类照存照传**;匹配时按**整串精确相等**处理(评审 I-30④)——老目录遇到新类能力(如 `ml:tpu`)仍可被精确查询,不会成为能力黑洞;
- 组合能力允许封装成单个团队约定标签,不必拆解——标签是给人及其"龙"约定的词汇表,注册中心不做语义校验;
- 负标签不做(声明"没有 X"是无穷集合)。

### 3.2 匹配语义(定案,评审 I-30)

| 规则 | 定义 |
|------|------|
| 无 `@` | offer 的类与值段须与节点标签**完全相等**(节点侧 `@版本` 段忽略)。**不是字符串前缀匹配**——`tool:node` 不命中 `tool:nodejs`、`tool:node-lts` |
| 带 `@` | 按 offer 所写段数**逐段比较,数字段按数值比较**:`tool:node@20` vs `tool:node@20.1` ✅(1 段 vs 前 1 段,20=20);`env:python@3` vs `env:python@3.12` ✅;`tool:node@20` vs `tool:node@18` ❌ |

正反例速查:

| offer 写 | 节点档案 | 匹配 |
|----------|----------|------|
| `tool:node` | `tool:node@20` | ✅ |
| `tool:node` | `tool:nodejs` | ❌(值段不相等) |
| `tool:node@20` | `tool:node@20.1` | ✅(逐段数值) |
| `tool:node@20` | `tool:node@18` | ❌ |
| `env:python@3` | `env:python@3.12` | ✅ |

v1 不做区间语法(`@>=18` 等谓词,需求出现再加)。

### 3.3 动态档案:负载

| 字段 | 说明 |
|------|------|
| `queue_depth` | 本地待办任务数(含已接受的远端任务) |
| `running` | 正在执行的任务数 |
| `accepting` | 布尔:当前是否愿意接新单(执行方自己的策略开关,如夜间不接) |
| `ts` / `ttl_ms` | 快照时刻与有效期(默认 60s) |

**过期判定基准**(评审 I-41):过期 = 注册中心以**本地收到该快照的时刻** + `ttl_ms` 计时;快照内 `ts` 仅展示——P5(不依赖跨机时钟)在跨文档处的落实。

`accepting=false` 是**礼貌提示而非闸门**:offer 仍可送达,执行方是否拒绝由它自己当场决定——与 P13 一致;即时停摆见 §6.3 的本地暂停开关(独立于本快照字段)。

## 4. 上报协议

- **全量上报**:enroll 时与 `PUT /v1/nodes/me/caps`(02 §9,整体替换语义——"以上报集合为准,未提及即删除",自愈摘标签依赖此语义)携带完整静态标签集;`PUT /v1/nodes/me/load` 上报负载快照。
- **静态变更**(装了新工具、换了环境):检测到即上报,无周期;**`caps_rev` 仅在静态标签集变更时自增**——动态刷新不 bump(评审 I-59),否则修订号退化为上报计数器,缓存失效失效。
- **动态刷新**:默认 60s 周期 + 事件触发(`accepting` 翻转、任务大进大出)。
- 上报走注册中心 HTTP,**不进 task.* 消息**——任务信封瘦身,"不上报负载"的老节点天然兼容。

## 5. 查询协议(牵头方视角)

```
GET /v1/teams/{id}/nodes?caps=tool:ios-sign&caps=tool:node@20&online=true
→ 200 [{node_id, name, online, platform, qlong_version, caps:[…], load:{…, ttl_ms}, caps_rev}]
```

- 过滤条件全匹配(caps 为 AND,重复参数编码见 02 §9);未知类按整串精确匹配(§3.1);`online=false` 的节点也返回(带最后档案),由牵头方决定要不要发暂存单。
- 动态档案过期时 `load` 返回 `null`,节点照常在列(P16);**过期基准 = 注册中心本地时刻**(§3.3)。
- **返回按 node_id 稳定排序,无评分**。负载加权、信任加权、往返成本——全是牵头方本地策略,协议不背(P14)。
- 响应含 `platform / qlong_version`,版本漂移有查询出口(评审 I-52)。

兜底通道:目录查询不到时,牵头方可发 `rpc.ask` 口头询问"你有没有 X"——互助场景的即兴能力发现。注册中心是索引,rpc.ask 是询问,两者并存。

## 6. 执行方自评(接单五道闸)

offer 到达后按序评估,任一不过 → 立即 `reject`(01 R6,禁止沉默):

| 闸 | 检查 | 拒绝方式 |
|----|------|----------|
| 1 签名 | 验签(01 §3.3,task.* 与 rpc.* 均必签) | **静默丢弃 + 审计**(回声分级,02 A6) |
| 2 策略 | **跨队(team 复核失败)→ 静默丢弃 + 审计**;同队本地策略(如夜间免打扰)→ 回执 | 跨队:丢弃;策略:`reject(policy_denied)`(评审 I-14,两者拆开) |
| 3 能力 | `required_caps` 逐条按 §3.2 匹配 | `reject(unsupported_caps)` |
| 4 负载 | `queue_depth`/`running` 超阈值、或与已有任务资源冲突 | `reject(busy, retry_after_ms?)` |
| 5 执行档案 | 任务所需权限(`requires`,§6.2)超出远端执行档案默认(§6.1)→ 按节点策略拒绝,或转本地人确认后放行 | `reject(policy_denied)`(或确认后放行) |

闸 3 拒绝时,`reject.detail` 附 `missing:[…]`(缺哪几条)——拒绝回执反哺牵头方改派(已关闭 01 篇原开放问题 5)。

### 6.1 远端任务执行档案(remote task profile)

**这是全系统最锋利的面,本文认领它**:执行方的"龙"将以本地真实权限,运行一条由牵头方 LLM 写成的任务书——不需要任何人被攻陷,一条写歪或被上游注入的 `summary` 就足以让队友机器做危险动作。"提示注入"不是攻击者的技巧,是常规路径的固有属性。因此:**一切远端来源的任务(kind=aid 与 kind=project 一律)默认套用低于本地任务的执行档案**;本机用户发起的本地任务不受影响。

| 维度 | 本地任务 | 远端任务默认 |
|------|----------|--------------|
| 工作区 | 用户授权范围 | **offer 携带 `workspace` 时:仅该目录,越界拒绝;未携带时(评审 I-32):仅一次性临时工作目录,产物只能经 `payload_ref` 回传,禁止读写任何既有路径**——或经 `requires` 声明 / 本地人确认后放行 |
| 工具 | 全部已装 | 节点策略白名单内 |
| 网络出口 | 不限 | 受限出口(白名单/代理),默认拒绝内网敏感网段;**payload 拉取行为一并纳入本约束**(评审 I-18,与 01 R10 解析基线叠加) |
| 凭证 | 环境内全部 | 不注入节点持有的敏感凭证(SSH key、API token、证书) |
| 敏感操作 | 自行执行 | 大范围删除、系统级安装、读取凭证等 → 需本地人确认 |

- 档案是**执行方本地策略**(配置预设);offer 只能*声明*需要什么(`requires`),永远不能*放宽*档案——权限的收窄权始终在执行方(P13 的延伸)。
- 档案缩窄的是**爆炸半径**,不承诺消除提示注入;残余风险由"敏感操作本地人确认"兜底——文档如实声明,不假装这是一个已被解决的问题。
- **同队执行面缓冲带**(评审 I-19,不改信封、不破坏 P7 的零成本缓解):① 节点对同队来源的 offer/rpc 设 per-source 速率上限,超限 `reject(busy, retry_after_ms)`;② 任意远端任务开始/结束本地可见通知(通知不阻断——用户对"我的机器正在为谁干活"有感知);③ 本地即时生效的"暂停接远端单"开关,语义独立于 `accepting` 快照(60s 时延不可接受)。

### 6.2 requires 与本地确认契约(评审 I-25)

`requires = [{class: tool|net|confirm, value, reason}]`:

- `class`: `tool`(白名单外工具)/ `net`(超出默认出口)/ `confirm`(显式请求人工确认级);
- `value`: 具体需求(如 `net:office-vpn`、`tool:ffmpeg`);
- `reason`: **必填,且面向本地人写**(人话,不是给 LLM 的)——它回答"为什么一个远端任务要读我的 SSH key";
- 未知 `class` 按 §3.1 向前兼容原则处理(照存照传,整串精确匹配);
- "确认级"允许 offer 显式请求,但执行方档案保留**最终否决权**(P13 重申)。

**本地确认提示渲染契约**(模板由执行方本地持有,发起方只供料):任务来源(node/team、hops 深度)+ `summary` 摘要 + `requires[].reason` + 将越界的档案维度列表。没有 `reason` 的越界请求,渲染层应默认拒绝倾向。

### 6.3 同队执行面缓冲带

见 §6.1 末条:per-source 速率上限、远端任务开始/结束本地通知、本地即时暂停开关。三者均为节点本地策略,不进协议、不改信封、不破坏 P7 的全互信消息面模型。

## 7. 反馈闭环与能力自愈(两段式,评审 I-20)

派单系统的能力档案必然漂移。v1 用最小闭环修正,不建主动探测;**自愈必须可见、可恢复、不误摘**:

```
task.fail(caps_missing) —— 仅允许来自本地确定性检查(评审 I-20①)
        │
牵头方:更新本地节点-能力记忆(软降权),改派时排除
        │
节点侧两段式:
  确定性检查失败,10 分钟内 ≥3 次 → cap_tag_suspected(软摘:档案保留,默认排除出候选)
      ├─ 24h 内无复发 → 自动恢复(硬摘未发生,标签回用)
      └─ 复发,或本地复核失败 → cap_tag_removed(硬摘)
  滞回:恢复后 24h 内不再自动摘(防抖动)
```

- **`caps_missing` 语义收紧**:仅当本地**确定性检查**(二进制/服务存在性、许可证文件等一次性轻量验证)失败才可发;禁止仅凭任务失败推断——docker daemon 没起、磁盘满、网络闪断归 `internal_error / payload_unavailable` 等瞬态码(01 §4.3);
- **区分"声明失真"与"需求错误"**:仅当 **≥2 个不同牵头方**重复命中同一标签才自动硬摘;单一来源重复失败只做牵头方侧降权,**不摘标签**(可能是牵头方需求写错,评审 I-20③);
- **摘除动作本地必现**:`qlong caps` 可查 + 本地通知/日志一条;`cap_tag_suspected / cap_tag_removed` 均进审计事件(01 §11)并计数上报;
- 主动探测(轻量 probe 实测能力)明确**不做**:成本高、且 NACK/失败回流已覆盖主要漂移场景。

## 8. 隐私边界

能力档案是机器画像,可见范围 = **本 team**(02 目录查询本就 team 鉴权);跨 team 不可见,v1 无例外;未来跨团队 grant 生效时,能力可见性必须作为 grant 的显式选项。

**留存与删除**(评审 I-47):节点 `revoked` 后,注册中心即删除其 caps/load 档案(审计日志按另行保留期处理);**标签披露最小化建议**:`net:` / `ext:` 类标签仅声明到类别(如 `net:office-vpn` 而非内网拓扑细节;`ext:github` 而非携带账号标识),降低画像精度。

## 10. 开放问题

1. **版本区间与组合匹配**:`@>=18`、`hw:ram>=32g` 谓词语法,等真实派单需求出现再定。
2. **能力实测(probe)**:高价值标签的注册时校验任务;与 §7 两段式自愈的"本地复核"衔接。
3. **负载之外的因素**:时区/时段偏好、电量、计费——先把 `accepting` 开关与 §6.3 暂停开关跑起来。
4. **跨团队能力可见性**:与 02 §12.3 的 grant 模型联动设计。
