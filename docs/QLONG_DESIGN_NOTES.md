# 群龙(Qlong)系统设计纪要

> 状态:架构方向已确定,详细设计未开始。
> 本文档是需求与架构讨论的沉淀,作为新项目的起点。所有"已确定"条目为讨论结论;"待设计"条目为后续设计工作的输入。
> 正式名:**群龙**(Qlong),取《周易·乾·用九》"见群龙无首,吉";命名释义见根目录 [README.md](../README.md)。

## 1. 愿景

以群龙单机程序(命令行 `qlong`)为基座,构建一个**分布式协作系统**:多台设备各自运行一个群龙实例,实例之间可以互相通讯,并作为一个整体协同完成项目/任务。

一句话概括架构原则:**中心做服务,边缘做决策**。

- 中心服务器只提供三类**基础设施服务**(注册、通讯、分发),**永不介入任务调度**;
- 调度的智能完全下沉到每一个节点——每条"龙"都是自治的"老板",自己接任务、自己拆解、自己干,也可以把子任务派给其他设备上的群龙。

### 边界(不是什么)

- 分布的是 **agent 实例和任务**,不是模型本身——不涉及 DeepSeek 模型的分布式推理/参数拆分;
- 不只是消息转发(那只是通讯,不是协同),核心是任务层面的编排、分工与汇总;
- 不重新发明冲突解决机制,复用成熟方案(见 §6)。

## 2. 总体架构

```
                 qlong.qianji.io(中心化基础设施,只做三件事)
        ┌──────────────┬───────────────┬────────────────┐
        │  节点注册中心   │   通讯服务器     │  群龙分发服务器   │
        │ 身份/发现/在线态 │ 消息路由/暂存     │  安装包/自动注册   │
        └──────────────┴───────────────┴────────────────┘
              ▲ 注册、心跳、查询节点        ▲  消息上行下行
              │                          │
    ┌─────────┴───┐        ┌──────────┴──┐        ┌────────────┐
    │  设备A:群龙  │ ◀─派单/互助─▶ │  设备B:群龙  │ ◀─────▶ │  设备C:群龙  │
    │  └ subagents │          │  └ subagents │        │  └ subagents │
    └─────────────┘          └─────────────┘        └────────────┘
              任务调度权在每一个节点内部(去中心化)
```

**拓扑结论:中心化与去中心化的结合。**

- **去中心化的部分 = 任务面**:没有全局调度器。任务调度由某个节点的群龙完成——分配给自己或自己的 subagent,也可以通过通讯机制分配给其他设备上的群龙。节点之间是对等的同伴关系:每一环都可能同时是任务的发起方、转包方和执行方。
- **中心化的部分 = 基础设施面**:节点注册、通讯服务器、群龙分发服务器,统一部署在 `https://qlong.qianji.io/`。

## 3. 中心化基础设施:qlong.qianji.io 的三个角色

| 服务 | 职责 | 关键点 |
|------|------|--------|
| 节点注册中心 | 节点身份的签发与登记、在线状态(心跳)、节点发现(通讯录) | 全网"通讯录 + 在场证明",让任意节点能知道"哪些同伴在线、如何联系" |
| 通讯服务器 | 节点间消息的路由中转、离线消息暂存与补投 | 设备多在 NAT 后,互连不可靠,基础形态是全经中心转发;中心兼做离线队列 |
| 群龙分发服务器 | 安装包下载、安装、**自动完成 Agent 注册** | 入网体验核心,见 §4 |

三个服务共同的特点是**"笨"**:它们不知道也不关心消息里装的是什么任务、该派给谁。类比:注册中心是工商局,通讯服务器是邮局,分发服务器是应用商店——没有一个是项目经理。

## 4. 入网体验(安装即注册)

任何可联网的设备访问 `https://qlong.qianji.io/install`:

```
下载安装包 → 安装群龙 → 自动完成 Agent 注册(无接触下发身份凭证)→ 入网在线
```

零手工配置。这隐含两条产品要求:

1. 注册流程必须完全自动,凭证在安装过程中签发,装完即在线;
2. 需要配套的**信任边界**设计:注册是开放/自动的,但消息可见范围与派单权限必须有归属界定(哪些设备算"我的"/同一团队的),否则任何陌生人都能互相通讯。(待设计,见 §8)

## 5. 去中心化任务面:调度权在节点

**不存在全局调度器。** 调度权属于每个节点自己的群龙:

- **对内**:接到任务后,拆解给自身和本地 subagent 执行(即群龙单机形态的工作方式,保留不动);
- **对外**:当任务超出本机能力(缺某个环境、缺算力、忙不过来),通过通讯机制把子任务**派给其他设备上的群龙**。对方的群龙同样拥有完整自治权,以同样方式决定自己干、拆给自己的 subagent、或继续转派。

单机场景下群龙照常独立工作;分布式能力是叠加的一层,单机形态完全保留。

> 边界澄清:「无首」治理的是**基础设施面**(中心永不调度)与**互助面**(无固定牵头者);在**项目级协同内部,牵头方就是该项目的「首」**——任务图谱在其内存中。这是有意取舍:首是任务的属性,不是系统的属性;且首可被接管(检查点 + 任务幂等,详见 01 篇 §12)。

## 6. 冲突处理:不发明新轮子

**已定原则**:同一条"龙"的多个会话今天就会改同一个文件,分布式只是把这个既有问题的范围扩大了。因此方向是**复用成熟机制**——任务级工作区隔离、文件锁、以 git 为核心的分支/合并工作流——把它从"单机多会话"自然推广到"跨设备多会话"。具体选型在详细设计阶段给出,不发明新的分布式共识算法。

## 7. 协同的两种模式(都要)

两种模式**复用同一条通讯通道**,区别只在消息语义层:

| 模式 | 形态 | 特征 |
|------|------|------|
| **项目级协同** | 一个项目由某台设备的群龙牵头,拆解成分工图谱,跨设备执行,再回收、校验、整合结果 | 有生命周期的编排过程;需要任务图谱与状态跟踪 |
| **日常互助** | 各设备的群龙平时各干各的任务,随时点对点求助:问问题、委托小事、借用只有对方设备才有的能力/环境 | 即兴、轻量、无固定结构;请求-应答语义 |

分布式的真正价值在各设备贡献**独有资源**:本地环境、文件系统、工具链、GPU 算力、网络位置。

## 8. 待设计清单(详细设计阶段的输入)

1. **通讯协议与消息模型**(地基,优先):消息封装格式、请求-应答语义、派单的可靠性语义(接单确认、进度心跳、超时回收、失败重派)、项目级协同的任务图谱/状态跟踪消息;
   → 初稿见 [QLONG_DESIGN_01_MSG_PROTOCOL.md](./QLONG_DESIGN_01_MSG_PROTOCOL.md);
2. **注册中心数据模型与信任边界**:节点身份结构、凭证签发与轮换、"我的设备/团队"的归属与授权模型(谁能和谁通话);
   → 初稿见 [QLONG_DESIGN_02_REGISTRY_TRUST.md](./QLONG_DESIGN_02_REGISTRY_TRUST.md);
3. **能力声明机制**:节点上报自己有什么(环境、工具、硬件),让派单决策能力感知;
   → 初稿见 [QLONG_DESIGN_03_CAPABILITY.md](./QLONG_DESIGN_03_CAPABILITY.md);
4. **文件协同具体机制**:在"成熟机制"原则下选型——git 工作流 / 工作区隔离 / 锁的具体方案;
5. **分发与安装器**:`/install` 的平台适配、安装脚本、自动注册的凭证下发流程;
6. **离线与弱网**:消息暂存策略、任务派发对离线节点的处理(等上线?改派?)。

> 评审注记:01–03 篇(协议/信任/能力)已成初稿,但它们是分布式任务系统中成熟套路最多的部分。**下一设计单元为 §8.4 文件协同与产物回传**,并以一次**双机纸面端到端走查**(拆解 → 派单 → 取码 → 执行 → 产物回传 → 校验整合)逼出 §8.4/§8.6 与 payload_ref 解析的全部隐藏决策——项目级协同没有文件机制就无法落地,差异化在文件与执行面,不在继续磨协议。
