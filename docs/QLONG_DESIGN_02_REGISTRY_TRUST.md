# 群龙详细设计 02:注册中心数据模型与信任边界

> 状态:**初稿,供评审**。
> 本文承接纪要(`QLONG_DESIGN_NOTES.md`)§8 第 2 项,并兑现 01 篇(`QLONG_DESIGN_01_MSG_PROTOCOL.md`)留下的两处接口:信封的 `team_id` 字段如何被执法(01 §9)、公钥目录如何运转(01 §3.3)。
> 账号体系(人如何登录 qlong.qianji.io)属产品侧,本文只定义**团队为信任域**及其归属字段;分发安装器(`/install` 的平台脚本)属纪要 §8.5,本文只定义 enrollment 协议侧。

## 1. 范围

**本文确定:** 身份三层模型(人/团队/节点)、注册入网流程(enrollment)、注册中心数据模型、凭证生命周期(签发/轮换/吊销)、信任边界与 ACL 规则、在线状态的权威来源、注册中心 API 面、威胁模型。

**本文不定:** 能力档案的字段细节(→ 03 篇)、通讯网关消息路由的内部实现、跨团队授权模型(v1 不做,见 §12)。

## 2. 设计原则(编号接续 01 篇 P1–P6)

- **P7 团队是信任域的原子**。信任按 team 划界,不按节点逐个授权。同队全互信(都是你的机器),跨队默认零信任。
- **P8 入网开放,协同需要归属**。解决纪要 §4 的内在张力:注册自动、零配置(纪要 D5);但**跨节点消息必须同 team**——未归属的节点是一台能独立工作的单机,不是一个能收发任务的网络成员。
- **P9 双重身份并存**。传输身份(node token,注册中心自签的访问令牌,节点对中心证明"我是已注册节点")+ 责任身份(Ed25519 私钥,节点对节点证明"这条消息是谁签的",01 D11)。两者丢失的后果与恢复路径不同,不可合并。
- **P10 双重执法**。ACL 在通讯网关的路由层执法(主,看得见信封头),在节点侧复核(辅,验签 + team 复核 + 策略)。单点执法必有单点失守。
- **P11 注册中心不学习任务语义**。纪要"笨中心"的延续:它知道你是谁、你在不在线、你声明了什么能力(03 篇),永远不知道也不需要知道任何任务。
- **P12 ACL 失败关闭**。查不到归属、验不了身份、状态不明 → 拒绝。发现类只读查询可走降级缓存,任务面不允许降级。

## 3. 身份模型

### 3.1 三层结构

```
人(User,产品账号体系)
 └─ Team(team_id,信任域,"我的设备"/"某项目组")
     └─ Node(node_id,一台设备上运行的一个群龙实例)
```

- **人**:可属于多个 team(个人设备组、公司项目组……)。账号体系本身(注册/登录/找回)是产品侧事务,注册中心只存 `owner_user_id` 引用。
- **团队**:信任域的原子(P7)。v1 每 team 一个 owner(创建者);成员管理(多人共管)是产品功能,不改变信任模型。
- **节点**:一个 team 内唯一别名 + 全局唯一 `node_id`(uuid)。一个节点同一时刻**只属于一个 team**(换队 = 退出重入)。
- **子代理不在注册中心**。`agent_id`(01 §3.1)是节点本地概念:注册中心只认到"某台设备",不认"设备里的哪个 subagent"。这同时缩小了数据面与攻击面——subagent 的生死、数量、命名对全网不可见。

### 3.2 凭证体系(自包含,无外部身份依赖)

每个节点有两类凭证,职责不同、不可互替:

| 凭证 | 形态 | 职责 | 失效后果 |
|------|------|------|----------|
| node token | 注册中心签发的不透明随机令牌(256-bit,服务端仅存哈希) | 对中心的常规认证:注册中心 API 调用、通讯网关握手 | 重新签发即可,节点身份不受影响 |
| Ed25519 密钥对 | 节点本地生成,公钥登记于注册中心(带 `key_epoch`) | 消息签名,节点间责任归属(01 §3.3) | 走 §6.1 轮换/吊销流程 |

token 是**通行证**(便捷、可随时吊销重发),密钥是**身份**(不可抵赖、轮换有纪元)。enroll 时一次签发两者:`POST /v1/enroll` 返回 `node_id / team_id / node_token / key_epoch`。

## 4. 注册入网流程(enrollment)

### 4.1 常规路径(登录状态,/install 即入队)

```
浏览器打开 qlong.qianji.io/install
  → 用户(可选)登录 → 页面生成一次性 enrollment token(绑定其 team)
  → 安装命令携带该 token:curl …/install.sh | sh -s -- --enroll <token>
  → 群龙安装完成,本地生成 Ed25519 密钥对
  → POST /v1/enroll → 返回 node_id / team_id / node token / key_epoch
  → 入网在线,进入该用户的 team
```

零手工配置(纪要 D5)得以保留的原因:**归属从用户的浏览器会话继承**,安装过程不需要用户输入任何身份信息。

### 4.2 未登录路径(先装后认领)

页面未登录时,安装命令不带 token:节点照常 enroll,注册中心为其创建**单机 team**(team = 自己,成员只有它)。此时节点是完全合格的单机群龙(纪要 §5:单机形态保留),但没有可通讯的同伴。事后认领:用户在控制台为目标 team 签发 enroll token,节点执行 `qlong join <token>` 换队。

`qlong join` = 以旧凭证认证、提交新 enroll token、注册中心原子地改 `team_id` 并刷新目录。换队后**旧 team 立即不可达**(目录与网关 ACL 同步更新)。

### 4.3 Enrollment token 属性

| 属性 | 值 |
|------|-----|
| 形态 | 128-bit 随机数,URL-safe |
| 绑定 | 签发时固定 `team_id` |
| TTL | 5 分钟,单次使用(used_by 记录消费节点,防重放) |
| 权限 | 仅 enroll,不能做任何其他事 |
| 签发人 | team owner(经控制台或 /install 页面) |

## 5. 注册中心数据模型

### 5.1 Team

| 字段 | 说明 |
|------|------|
| `team_id` | uuid,主键 |
| `name` | 显示名,可重复 |
| `owner_user_id` | 产品账号引用 |
| `created_at` | — |

### 5.2 Node(核心表)

| 字段 | 说明 |
|------|------|
| `node_id` | uuid,主键,注册中心签发 |
| `team_id` | 当前归属,唯一 |
| `name` | team 内唯一别名(网关寻址的人读形式) |
| `pubkey` / `key_epoch` | 当前签名公钥与纪元(§6.2) |
| `status` | `active` / `suspended` / `revoked`(状态机见下) |
| `platform` / `qlong_version` | 诊断与版本漂移可见性 |
| `caps_rev` / `load` | 能力档案引用与负载快照(→ 03 篇) |
| `last_seen` | 最后一次注册中心交互时刻,**仅诊断**(在线权威 ≠ 此字段,§8) |
| `joined_at` | — |

节点状态机:`active ⇄ suspended`(owner 手动暂停/恢复)→ `revoked`(终态,owner 吊销)。重装设备 = 新 enroll = 新 `node_id`,旧节点由 owner 清理;v1 不做自动替换标记。

### 5.3 EnrollmentToken

`token` / `team_id` / `created_by` / `expires_at` / `used_by?` / `consumed_at?`。用后保留记录(审计),不可复用。

## 6. 凭证生命周期

### 6.1 三种凭证失效场景与恢复

| 场景 | 动作 |
|------|------|
| 常规轮换 | 节点发起 `POST /v1/nodes/me/keys`(token 认证 + 当前私钥对请求签名)→ 注册中心存新公钥,`key_epoch` +1。双因子:丢了 token 用不了,丢了私钥签名过不了 |
| 设备丢失/密钥疑似泄露 | owner 将节点 `suspended` → 节点重装后 `qlong join` 新 enroll token → 新 node_id,旧节点 `revoked` |
| owner 主动移除 | `revoke`:node token 吊销 + 状态 revoked + 网关停路由,一次操作三处生效 |

### 6.2 key_epoch 的传播语义

验证方按 `(node_id, key_epoch)` 缓存公钥(01 §3.3)。缓存未命中 → 查注册中心;查到 `revoked` 或不存在 → **负缓存**(TTL 10 分钟)+ 拒签。不设"主动推送吊销"机制:网关路由层已经在消息到达对端之前拦截(P10),节点侧的负缓存只是第二道防线,不需要强一致的吊销广播。

## 7. 信任边界与 ACL(v1 规则)

| # | 规则 | 执法点 |
|---|------|--------|
| A0 | **from 钉扎**:信封自报的 `from.node_id / from.team_id` 与连接身份(及目录归属)不一致 → 直接拒绝路由 + 审计;一致则以钉扎值为准进入后续规则。诚实发送者无感(自报值即真实值,`sig` 校验不受影响);`from.agent_id` 为节点本地概念,不参与钉扎 | 网关 |
| A1 | `from.team_id ≠ to.team_id` → 拒绝路由,审计。`to.team_id` 缺省时由目录反查(带缓存);比对一律基于钉扎后的 from | 网关(主) |
| A2 | 发送节点不在目录 / 非 active → 拒绝路由 | 网关(主) |
| A3 | 连接认证:node token 无效 → 连接拒绝(消息根本进不来) | 网关连接层 |
| A4 | 验签失败(task.* 与 rpc.* **均必签**)→ 丢弃 + 审计,不回声(01 §3.3) | 节点(辅) |
| A5 | 节点复核:`from.team_id ≠ 本地 team` → `reject(policy_denied)` | 节点(辅) |

- **同 team = 全互信**:team 内节点互相可发现、可问答、可派单,无细分权限。理由:team 的语义就是"我的机器们";细分(访客节点、借入算力)是真实需求但属策略模型扩展,见 §12。
- **跨 team = 零可达,且两条路径都闭合**:经网关——A0 先把伪造的 `from` 钉回发送者真实身份,A1 随即失配,消息出不了网关;不经网关(01 §9 v1.5 局域网直连)——A4 验签(rpc 同样必签)与 A5 复核构成节点侧防线,伪造者无法伪造受害节点的签名。**若没有 A0,自报 `from` 可指向任意受害团队:A1/A2 比对的都是自报字段,伪造者全部放行;而 `rpc.*` 一度无签名要求,A4 无从拦截——任一活跃节点可跨队 `rpc.ask` 套取对方能力与状态。**此洞已由 A0 + rpc 必签闭合(评审修订)。未来跨团队协同(显式授权对、限时 grant)有明确演进位:`to.team_id` 字段已存在,加 grant 表即可,不动信封。
- 网关执法只看信封头(01 P3),v1 **不验签**(性能与职责分离:网关管"该不该路由",节点管"是不是本人说的")。

## 8. 在线状态(presence)

- **权威来源 = 通讯网关的连接态**。所有消息经中心转发(纪要 §3),连接即在线、断开即离线——不发明第二套心跳协议。网关维护的连接表就是通讯录的在线标志。
- 注册中心 `last_seen` 仅用于诊断与运营统计(多少设备还活着),不参与任何派单判断。
- 离线不是异常状态而是常态(纪要 §8.6):对离线节点的 offer 走收件箱暂存 + `offer_ttl`(01 §9/R2),发现类查询对离线节点返回"离线 + 最后能力档案"(03 篇)。

## 9. API 面(v1 草案)

| 端点 | 方法 | 鉴权 | 作用 |
|------|------|------|------|
| `/v1/enroll` | POST | enrollment token | 注册入网(§4) |
| `/v1/nodes/me` | GET / PATCH | node token | 自查/更新(name、caps、load) |
| `/v1/nodes/me/keys` | POST | node token + 当前私钥签名 | 密钥轮换(§6.1) |
| `/v1/teams/{id}/nodes` | GET | team 成员 token | 通讯录:成员 + 在线态 + caps 摘要(→ 03) |
| `/v1/nodes/{id}/pubkey` | GET | team 成员 token | 公钥目录(仅同 team 可查,缩小暴露面) |
| `/v1/teams/{id}/enroll-tokens` | POST | owner | 签发邀请/认领令牌 |
| `/v1/nodes/{id}/revoke` `…/suspend` | POST | owner | 吊销/暂停 |

无独立的 `/heartbeat` 端点:在线走网关连接态(§8),负载与版本刷新走 `/v1/nodes/me` PATCH(03 篇),避免第三条上报通路。

## 10. 威胁模型(v1 防什么、不防什么)

| 威胁 | 缓解 | 残余风险 |
|------|------|----------|
| 陌生节点互发消息/派单 | A1/A4/A5 三层拦截 | — |
| 伪造发送者 | Ed25519 验签(01 D11) | 私钥泄露(见下行) |
| 密钥泄露 | 轮换 + epoch 失效旧钥;suspend/revoke 通道 | 轮换前的窗口内消息可伪造 |
| 被吊销节点残留作恶 | 网关拒路由(即时)+ 节点负缓存(次秒级窗口) | 已投递到对端收件箱的离线消息,上线后 A4/A5 仍拦 |
| enrollment token 重放 | 单次使用 + 5 分钟 TTL | — |
| 中心被攻陷 | 可见信封头(谁给谁发过什么);body 未加密前可读 | `enc` 启用前,body 机密性依赖传输 TLS 与中心自律 |
| TOFU 首连中间人 | v1 接受(与 ssh 首连同级) | 首连即被劫持的场景;固化方案见 §12 |
| **远端任务书被注入/写歪(常规路径,无需任何人被攻陷)** | 执行方第五道闸:**远端任务执行档案**——工作区限定、工具白名单、网络出口受限、凭证不注入、敏感操作本地人确认(03 §6.1) | 档案缩窄爆炸半径,不消除注入;残余风险由本地人确认兜底 |
| **团队内成员机器被攻陷** | **无**——同队全互信是消息面的模型前提 | 固有风险;执行档案(03 §6.1)同样缩窄其在执行面的爆炸半径 |

## 11. 决策记录(接续 01 篇 D6–D12)

| # | 决策 | 结论 |
|---|------|------|
| D13 | 信任域 | 信任按 team 划界;同队全互信,跨队零可达;入网开放、协同需归属(P7/P8) |
| D14 | 归属继承 | /install 登录态经一次性 enroll token 继承用户 team;未登录装成单机 team,事后 `qlong join` 认领 |
| D15 | 身份实现 | 两类凭证(node token + Ed25519 密钥对)与公钥/团队/状态全部由注册中心自签自管,无外部身份依赖 |
| D16 | 执法分层 | 网关管"该不该路由"(看头,不验签),节点管"是不是本人"(验签+复核) |
| D17 | 在线权威 | 网关连接态;注册中心不设心跳端点,`last_seen` 仅诊断 |

## 12. 开放问题

1. **跨团队授权(grant)模型**:显式授权对、有效期、可撤销;`to.team_id` 已预留,信封不动。
2. **团队内信任细分**:访客节点(朋友的机器贡献 GPU)的策略标签、per-node 出口限制。
3. **TOFU 固化**:首次 enroll 时由中心签名背书(证书链)或指纹比对,消除首连 MITM 窗口。
4. **注册中心高可用**:目录与 token 面有状态,需多副本方案;网关路由面应保持无状态可横扩。
5. **owner 的多人与审计**:多人共管 team 时的审批流。
