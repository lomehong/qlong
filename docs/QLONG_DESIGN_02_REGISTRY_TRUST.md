# 群龙详细设计 02:注册中心数据模型与信任边界

> 状态:**v2,已整合评审委员会修订**(行内以「评审 I-xx」标注来源,见 `QUNLONG_DESIGN_REVIEW_REPORT.md`)。
> 本文承接纪要 §8 第 2 项,并兑现 01 篇留下的接口:信封 `from`/`to` 的钉扎与锚定(01 §9、本文 §7)、公钥目录(01 §3.3)。
> 账号体系(人如何登录 lomehong-qlong.ms.show)属产品侧——其**最小操作面**已列入纪要 §8.7(评审 I-21);分发安装器的平台脚本属纪要 §8.5,本文只定义 enrollment 协议侧。

## 1. 范围

**本文确定:** 身份三层模型(人/团队/节点)、注册入网流程(enrollment,含防滥用基线)、注册中心数据模型、凭证生命周期(签发/轮换/吊销,**纪元现势性**)、信任边界与 ACL(含 **from/to 双向锚定**、**回声分级**)、目录-网关一致性、在线状态权威、注册中心 API 面(错误契约、并发语义)、威胁模型。

**本文不定:** 能力档案字段细节(03 篇)、**网关集群化形态(有状态横扩,§12.1)**、owner 账号体系与控制台实现(纪要 §8.7)、跨团队授权模型(v1 不做,§12)。

## 2. 设计原则(编号接续 01 篇)

- **P7 团队是信任域的原子**。信任按 team 划界,不按节点逐个授权。同队全互信(都是你的机器),跨队默认零信任。
- **P8 入网开放,协同需要归属**。注册自动、零配置(纪要 D5);但跨节点消息必须同 team——未归属的节点是一台能独立工作的单机,不是一个能收发任务的网络成员。
- **P9 双重身份并存**。传输身份(node token,注册中心自签的访问令牌)+ 责任身份(Ed25519 私钥,01 D11)。两者丢失的后果与恢复路径不同,不可合并。
- **P10 双重执法**。ACL 在通讯网关的路由层执法(主,看得见信封头),在节点侧复核(辅,验签 + team 复核 + 策略)。单点执法必有单点失守。
- **P11 注册中心不学习任务语义**。纪要"笨中心"的延续:它知道你是谁、你在不在线、你声明了什么能力(03 篇),永远不知道也不需要知道任何任务。
- **P12 ACL 失败关闭**。查不到归属、验不了身份、状态不明 → 拒绝。发现类只读查询可走降级缓存,任务面不允许降级。

## 3. 身份模型

### 3.1 三层结构

```
人(User,产品账号体系)
 └─ Team(team_id,信任域,"我的设备"/"某项目组")
     └─ Node(node_id,一台设备上运行的一个群龙实例)
```

- **人**:可属于多个 team。账号体系本身是产品侧事务,注册中心只存 `owner_user_id` 引用。
- **团队**:信任域的原子(P7)。v1 每 team 一个 owner;成员管理(多人共管)是产品功能,不改变信任模型。
- **节点**:一个 team 内唯一别名 + 全局唯一 `node_id`(uuid)。一个节点同一时刻只属于一个 team(换队 = 退出重入)。
- **子代理不在注册中心**。`agent_id` 是节点本地概念,注册中心只认到"某台设备",不认"设备里的哪个 subagent"。

### 3.2 凭证体系(自包含,无外部身份依赖)

| 凭证 | 形态 | 职责 | 失效后果 |
|------|------|------|----------|
| node token | 注册中心签发的不透明随机令牌(256-bit,服务端仅存哈希) | 对中心的常规认证:注册中心 API、通讯网关握手 | 重新签发即可,节点身份不受影响 |
| Ed25519 密钥对 | 节点本地生成,公钥登记于注册中心(带 `key_epoch`) | 消息签名,节点间责任归属(01 §3.3) | 走 §6.1 轮换/吊销流程 |

token 是**通行证**(可随时吊销重发),密钥是**身份**(不可抵赖、轮换有纪元)。enroll 时一次签发两者:`POST /v1/enroll` 返回 `node_id / team_id / node_token / key_epoch`。

**人类操作面的鉴权主体**(评审 I-21):owner 及其控制台属于产品账号体系——**owner 端点经产品侧用户会话代持调用,其认证机制属产品侧**;本文 API 面中的"team 成员"鉴权一律复用 **node token**(注册中心校验其 `team_id = {id}` 且节点 active),**不引入第三种凭证**。v1 控制台以 API-only 起步可接受,等价操作路径 = 控制台后端持产品会话调 owner 端点。

## 4. 注册入网流程(enrollment)

### 4.1 常规路径(登录状态,/install 即入队)

```
浏览器打开 lomehong-qlong.ms.show/install
  → 用户(可选)登录 → 页面生成一次性 enrollment token(绑定其 team,TTL 见 §4.3)
  → 安装命令携带该 token(经 stdin/env 传递,不进命令行,评审 I-16②):
      Unix:   curl -fsSL https://lomehong-qlong.ms.show/install.sh | sh -s -- --enroll-stdin
      Windows:[PowerShell 等效形态占位——平台矩阵见纪要 §8.5,评审 I-22③]
  → 群龙安装完成,本地生成 Ed25519 密钥对
  → POST /v1/enroll(请求体:enrollment token + pubkey + platform + qlong_version,评审 I-60)
  → 返回 node_id / team_id / node token / key_epoch → 入网在线,进入该用户的 team
```

零手工配置(纪要 D5)的原因:**归属从用户的浏览器会话继承**。安装命令示例以 Unix 为准标注,Windows 等效形态在纪要 §8.5 平台矩阵中定稿。

### 4.2 未登录路径(先装后认领)

页面未登录时,安装命令不带 token:节点照常 enroll,注册中心为其创建**单机 team**(成员只有它;`owner_user_id` 可空,评审 I-48)。此时节点是完全合格的单机群龙,但没有可通讯的同伴。事后认领,`join` 分两形态(评审 I-48②)——

- **join(换队)**:旧凭证 + 新 enroll token 双因子,原子改 `team_id`,node_id/密钥/历史保留;
- **join(重装恢复)**:仅凭 enroll token,等价于绑定目标 team 的全新 enroll,产生**新 node_id**(§6.1 场景)。

join 前置检查:存在在途远端租约或未消费 offer 时要求显式确认,成功后提示"旧 team 的牵头方将按租约超时回收你的任务"。换队后旧 team 立即不可达(目录 epoch 推进,§7.1)。

**单机 team 的生命周期**(评审 I-48①):`orphan`(零成员)/`self-owned`(有成员)/`active`(有 owner)。零成员孤儿 team 按 GC 策略清除(默认 30 天);活跃单机 team 保留并标注。

### 4.3 Enrollment token 属性

| 属性 | 值 |
|------|-----|
| 形态 | 128-bit 随机数,URL-safe;**经 stdin/env 传递,不进 shell history / 进程参数**(评审 I-16) |
| 绑定 | 签发时固定 `team_id` |
| TTL | **默认 30 分钟**(/install 页面生成;控制台手工签发可配)——覆盖"新机器下载安装"的真实链路;单次使用,重放窗口论证见 §10(评审 I-23) |
| 消费时点 | `consumed_at` 仅在 **enroll 成功响应时原子写入**;受理中的重复提交幂等(返回同一结果或 409 `enroll_token_in_flight`)(评审 I-23②) |
| 权限 | 仅 enroll |
| 签发人 | team owner(经控制台或 /install 页面) |

**安装器错误呈现契约**(评审 I-23③):对 `enroll_token_expired / enroll_token_used / enroll_token_invalid` 必须输出人话("邀请码已过期,请回到 /install 页面重新生成,重跑同一安装命令即可")并附重新生成入口深链。

## 5. 注册中心数据模型

### 5.1 Team

| 字段 | 说明 |
|------|------|
| `team_id` | uuid,主键 |
| `name` | 显示名,可重复 |
| `owner_user_id` | 产品账号引用;**单机 team 可空**(评审 I-48) |
| `state` | `active` / `self-owned` / `orphan`(派生,§4.2) |
| `created_at` | — |

### 5.2 Node(核心表)

| 字段 | 说明 |
|------|------|
| `node_id` | uuid,主键,注册中心签发 |
| `team_id` | 当前归属,唯一 |
| `name` | team 内唯一别名(网关寻址的人读形式) |
| `pubkey` / `key_epoch` | 当前签名公钥与纪元;**历史公钥按 `(node_id, key_epoch)` 单调追加保留(≥ 最近 3 个),供轮换窗口验签与审计**(评审 I-15,§6.2) |
| `status` | `active` / `suspended` / `revoked` |
| `platform` / `qlong_version` | 诊断与版本漂移可见性 |
| `caps_rev` / `load` | 能力档案引用与负载快照;**`caps_rev` 仅在静态标签集变更时自增**(动态时效由快照 ttl 承担,评审 I-59) |
| `last_seen` | 最后一次注册中心交互时刻,仅诊断(在线权威 = 网关连接态,§8) |
| `joined_at` | — |

节点状态机:`active ⇄ suspended`(owner 手动暂停/恢复)→ `revoked`(终态)。重装设备 = 新 enroll = 新 `node_id`,旧节点由 owner 清理。

### 5.3 EnrollmentToken

`token` / `team_id` / `created_by` / `expires_at`(TTL 默认 30 分钟) / `used_by?` / `consumed_at?`(原子时点,§4.3)。用后保留记录(审计),不可复用。

## 6. 凭证生命周期

### 6.1 失效场景与恢复

| 场景 | 动作 |
|------|------|
| 常规轮换 | `POST /v1/nodes/me/keys`(token 认证 + 当前私钥对请求签名)→ 注册中心存新公钥(历史保留),`key_epoch` +1。**请求签名要素**(评审 I-03③):`signature_input = JCS({method, path, sha256(body), ts, nonce})`,规范化与信封同一套 JCS 规则。双因子取舍的代价如实声明:**任一因子单独失效即无法自助轮换**,坠落为下行路径(评审 I-46) |
| 设备丢失/密钥疑似泄露 | owner `suspended` → 重装后 join(重装恢复,新 node_id)→ 旧节点 `revoked`。运维代价如实声明:**换身份 = trace 连续性断裂**,需 owner 清理旧节点并知会牵头方(评审 I-46) |
| owner 主动移除 | `revoke`:node token 吊销 + 状态 revoked + 网关停路由 + 网关**主动断开现有连接(close code 4002)**(评审 I-14) |
| **凭证全失 / 仅 token 失效** | 同"设备丢失"路径:重装 + 新 node_id(评审 I-46) |

**suspend 语义边界**(评审 I-46):suspend 停用 token 与网关路由(close code 4001),**不吊销密钥**——v1.5 直连路径下被窃设备仍可签名,由对端验签后的纪元现势校验(§6.2)与 A5 复核兜底;验证方对非 active 节点的纪元应回源拒绝。残余风险见 §10。

### 6.2 key_epoch 的现势性与轮换窗口(评审 I-15)

验证判据:**缓存命中且该 `key_epoch` == 注册中心目录当前纪元**才通过;纪元不匹配(含比当前旧)→ 回源复核。正缓存必须带 TTL,并随 suspend/revoke 事件失效(§7.1 目录 epoch 推送)。目录按 `(node_id, key_epoch)` 保留历史公钥(§5.2):轮换窗口内 in-flight 与收件箱补投的旧 epoch 消息仍可验签,"至少一次"承诺不被轮换打穿。「查无此 epoch」与「已吊销」返回**不同错误码**;负缓存仅适用于确认从未存在的 epoch。

## 7. 信任边界与 ACL(v1 规则)

| # | 规则 | 执法点 |
|---|------|--------|
| A0 | **from 钉扎**:信封自报 `from.node_id / from.team_id` 与连接身份(及目录归属)不一致 → 拒绝路由 + 审计;一致则以钉扎值为准。诚实发送者无感(`sig` 校验不受影响);`from.agent_id` 不参与钉扎 | 网关 |
| A1 | **恒以目录为锚**(评审 I-13):`to_team := 目录反查(to.node_id).team_id`(缓存 + 失败关闭,P12);`from.team_id ≠ to_team` → 拒绝路由 + 审计。**信封自报 `to.team_id` 仅作一致性核对,与目录不符 → 拒绝路由 + 审计告警**(伪造信号);`to.team_id` 留空合法。**回程消息(reject/answer 等)的 `to` 同样按发起方目录归属锚定** | 网关(主) |
| A2 | 发送节点不在目录 / 非 active → 拒绝路由 + 审计 | 网关(主) |
| A3 | 连接认证:node token 无效 → 连接拒绝 | 网关连接层 |
| A4 | 验签失败(task.* 与 rpc.* 均必签)→ 静默丢弃 + 审计(01 §3.3.4) | 节点(辅) |
| A5 | 节点复核:钉扎后跨队 → **静默丢弃 + 审计**(回声分级,见 A6);同队但本地策略拒绝 → `reject(policy_denied)` 保留回执 | 节点(辅) |
| **A6** | **回声分级**(评审 I-14/D28):**未认证/伪造场景一律静默**——验签失败、`exp` 过期、`to.node_id ≠ 本机`、钉扎后跨队;**已认证发送方本人可见**——A1/A2 的消息级拒绝允许网关向发送方本人回送 `routing.denied {rule, reason_code}`(仅诊断与体验,不参与可靠性);**suspend/revoke 时网关主动断开该节点现有连接并带语义 close code(4001 suspended / 4002 revoked)**,节点本地呈现"本机已被团队 owner 暂停"——复用连接做反馈信道,不新增探测面 | 网关 |

- **同 team = 全互信**(消息面):team 内节点互相可发现、可问答、可派单。执行面的缓冲带(速率上限、任务可见性、本地暂停开关)见 03 §6.3(评审 I-19)。
- **跨 team = 零可达,两条路径都闭合**:经网关——A0 钉扎 + A1 目录锚定(from/to 双向),伪造值在网关即死;不经网关(v1.5 直连)——A4 验签(rpc 同样必签)与 A5 复核兜底。**自报 `to.team_id` 的跨队穿透(评审 I-13)已由 A1 目录锚定闭合**,并配确定性测试:「to.team_id 伪造必须被网关拒绝」。
- 网关执法只看信封头(01 P3),v1 **不验签**(职责分离:网关管"该不该路由",节点管"是不是本人说的")。

### 7.1 目录-网关一致性(评审 I-45)

目录引入单调版本号 **directory epoch**:`join` 换队、suspend、revoke、密钥轮换时 bump 并**主动推送**到各网关实例(网关为目录变更的订户,§9)。A0/A1 的目录缓存记录携带 epoch,落后即回源——"换队后旧 team 立即不可达"由此获得机制保证,而非依赖缓存 TTL 自然过期。

## 8. 在线状态(presence)

- **权威来源 = 通讯网关的连接态**。连接即在线、断开即离线——不发明第二套节点级心跳协议。**辨析**(评审 I-50):本节"在线"是**节点级 presence**;01 R3 的 `task.progress` 租约心跳是**任务层**语义,两者正交。
- 注册中心 `last_seen` 仅诊断,不参与派单判断。
- **离线暂存范围**(评审 I-53):对离线节点的 **project 类** offer 走收件箱暂存 + offer_ttl(01 §9/R2);**aid 类不暂存**(目标离线即回执 `rejected(offline_not_stored)`,见 01 §9)。
- **已知限制**(评审 I-42):直连可达但网关离线的节点,v1 一律按离线处理;v1.5 直连落地时需重定义 presence 与"不可达"判定,列入回归范围。

## 9. API 面(v1 契约)

| 端点 | 方法 | 鉴权 | 作用 |
|------|------|------|------|
| `/v1/enroll` | POST | enrollment token(请求体:token + pubkey + platform + qlong_version,评审 I-60) | 注册入网;**并发语义:同一单次 token 并发提交,恰好一端 200,另一端 409 `enroll_token_used`**(评审 I-31) |
| `/v1/nodes/me` | GET / PATCH | node token | GET 自查;PATCH 仅标量字段(name 等) |
| `/v1/nodes/me/caps` | PUT | node token | **全量替换**静态标签集("以上报集合为准,未提及即删除",评审 I-29) |
| `/v1/nodes/me/load` | PUT | node token | 负载快照替换(60s 周期 + 事件触发) |
| `/v1/nodes/me/keys` | POST | node token + 当前私钥签名 | 密钥轮换(§6.1) |
| `/v1/teams/{id}/nodes` | GET | node token(校验其 `team_id = {id}` 且 active) | 通讯录:成员 + 在线态 + caps 摘要 + `platform`/`qlong_version`;分页:v1 全量返回,`next_cursor` 字段预留(评审 I-52) |
| `/v1/nodes/{id}/pubkey` | GET | node token(同 team) | 公钥目录;按 `(node_id, key_epoch)` 查询,含历史纪元(§6.2) |
| `/v1/teams/{id}/enroll-tokens` | POST | owner(产品会话代持,评审 I-21) | 签发邀请/认领令牌 |
| `/v1/nodes/{id}/revoke` `…/suspend` | POST | owner(产品会话代持) | 吊销/暂停(触发 §7.1 epoch 推送 + 网关断连) |

- **统一错误信封**(评审 I-31):`{error:{code, message, retryable?, details?}}`;错误码表初版:`enroll_token_invalid / enroll_token_expired / enroll_token_used / enroll_token_in_flight / not_team_member / node_revoked / node_suspended / key_epoch_conflict / rate_limited`。
- **查询参数**(评审 I-31):`caps` 过滤用重复参数(`?caps=tool:ios-sign&caps=tool:node@20`),值按 RFC 3986 编码。
- **限流与配额**(评审 I-16):`/v1/enroll` 与 `/install` 按 IP/ASN 限流;每 owner 节点数配额;长期未认领、长期离线的单机 team/节点执行 GC(§4.2)。
- **目录-网关系**:网关是目录变更的订户(§7.1);目录 API 的 `online` 字段来自网关连接态。
- 无独立 `/heartbeat` 端点:在线走网关连接态,负载刷新走 `PUT /v1/nodes/me/load`。

## 10. 威胁模型(v1 防什么、不防什么)

| 威胁 | 缓解 | 残余风险 |
|------|------|----------|
| 陌生节点互发消息/派单 | A0/A1/A4/A5 多层拦截 | — |

## 12. 开放问题

1. **网关集群化**(评审 I-12/ARCH):预期节点规模与消息速率?连接注册(Redis pub/sub 或 gossip)、node_id 分片路由、收件箱共享持久存储——三件套与 01 §13.5 同场设计;**网关是有状态组件**(连接表 + 收件箱),有状态横扩是核心架构件,不存在"保持无状态"的便宜路径。
2. **owner 账号体系与控制台**(纪要 §8.7):登录方式、会话形态(浏览器会话 vs PAT)、成员管理审批流;v1 API-only 起步(§3.2)。
3. **跨团队授权(grant)模型**:`to.team_id` 已存在,加 grant 表即可;能力可见性作为 grant 显式选项(03 §8)。
4. **团队内信任细分**:访客节点的策略标签、per-node 出口限制。
5. **目录多副本与高可用**:目录与 token 面有状态,需多副本;directory epoch 机制(§7.1)与副本一致性衔接。
6. **key transparency / 证书链路线图**(评审 I-17③):替代"注册中心 = 事实 CA"的运行期信任方案,列 v1.x+;v1 过渡期信任假设已如实写入 §10。
