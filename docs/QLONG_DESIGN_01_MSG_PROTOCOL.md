# 群龙详细设计 01:消息信封与派单可靠性语义

> 状态:**初稿,供评审**。
> 本文承接《群龙系统设计纪要》(`QLONG_DESIGN_NOTES.md`,下称"纪要")§8 待设计清单的第 1 项,并把第 2 项(身份/信任)中与信封咬合的最小部分一并定下——理由见 §2 原则 P1。
> 传输通道本身仍待选型(纪要 D3),本文只约定**信封与语义,传输无关**,并给出 v0 绑定建议(§9)。

## 1. 范围

**本文确定:**

- v1 消息信封的全部字段(§3);
- 消息类型族:日常互助与项目级协同如何塌缩为一族任务消息(§4);
- 派单的生命周期与双方状态机(§5);
- 可靠性规则:投递假设、幂等、租约、超时回收、撤销、NACK、重试改派(§6);
- 委托链与环防护(§7)、版本演进(§8)、传输绑定草案(§9)、默认参数(§10)。

**本文不定**(留给后续篇目):注册中心数据模型与 ACL 策略(纪要 §8.2)、能力声明格式(§8.3)、文件协同与 payload 存储选型(§8.4)、项目任务图谱的编排细节、分发安装器。

## 2. 设计原则

- **P1 信封一次定死**。身份、追踪、幂等、租约、版本五类字段必须进 v1 信封,即使初期策略从简。事后给协议补鉴权与追踪是著名的痛苦工程;字段之间互相咬合(寻址依赖身份,去重依赖 ID 体系),拆开设计必然返工。
- **P2 传输无关**。信封是自包含的 JSON 对象,不依赖底层通道提供顺序、去重或可靠性——这些由 §6 规则在端上保证。换通道不换语义。
- **P3 中心只见头,不读 body**。信封头(寻址、类型、ID)对中心可见,用于路由、ACL 与审计;body 对中心不透明。这是"中心做服务、永不介入调度"在协议上的投影,并为将来端到端加密预留 `enc` 字段。
- **P4 一切消息至少一次、执行必须幂等**。不做恰好一次——离线暂存意味着重投是常态。去重靠 ID 体系(§3.2),不在传输层解决。
- **P5 相对时长,不依赖跨机时钟**。所有超时/租约/有效期用相对毫秒数,由接收方收到时换算为本地绝对时刻。`ts` 仅为诊断字段,不参与任何顺序或过期判断。
- **P6 传引用不传负载**。大负载(代码、产物、日志)一律以引用传递,引用结构壳子在本文明确定义,存储选型留给纪要 §8.4。

## 3. 消息信封 v1

### 3.1 字段表

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `v` | int | ✅ | 协议主版本,当前 `1` |
| `type` | string | ✅ | 消息类型,点分命名 `族.动作`(§4) |
| `msg_id` | uuid | ✅ | 本条消息唯一 ID。传输层去重与审计用 |
| `ts` | RFC3339 | ✅ | 发送时刻,**仅诊断**,见 P5 |
| `from` | obj | ✅ | `{node_id, team_id?, agent_id?, key_epoch}`。发送方节点;`agent_id` 标识本地哪个子代理发起;`key_epoch` 为签名密钥纪元(§3.3) |
| `to` | obj | ✅ | `{node_id, team_id?}`。**任务面禁止广播**,一对一必填 |
| `reply_to` | uuid | — | 应答类消息关联的请求 `msg_id` |
| `trace` | obj | ✅ | `{trace_id, parent_span, origin_node}`。全链路追踪上下文,随委托链透传(§7) |
| `hops` | int | task.* 必填 | 委托深度。发起为 0,每转派 +1,上限 `MAX_HOPS`(§7) |
| `task_id` | uuid | task.* 必填 | **逻辑任务实例** ID,跨重投、跨改派稳定 |
| `attempt` | int | task.* 必填 | 执行权纪元,默认 1。每次重试/改派/回收重派 +1(兼作幂等与僵尸防护键,见 §6) |
| `sig` | obj | task.* / rpc.* 必填 | `{alg, key_id, value}`,对头+body 规范序列化的签名(§3.3) |
| `body` | obj | ✅ | 类型相关负载,**中心不透明** |

四个 ID 的分工——这是全文最容易混的一处,先钉死:

| ID | 粒度 | 谁生成 | 用途 |
|----|------|--------|------|
| `trace_id` | 一次用户任务的全链路 | 最初发起节点 | 跨节点排障、日志聚合 |
| `task_id` | 一个逻辑子任务 | 牵头方 | 幂等去重、状态机主键 |
| `attempt` | 该任务的一次派发执行 | 牵头方递增 | 重投去重、改派隔离、僵尸结果拒收 |
| `msg_id` | 一条消息 | 发送方 | 传输去重、`reply_to` 关联 |

### 3.2 示例

```json
{
  "v": 1,
  "type": "task.offer",
  "msg_id": "9f1c...-a2",
  "ts": "2026-09-06T12:00:00+08:00",
  "from": { "node_id": "node-a", "team_id": "t-lab", "key_epoch": 3 },
  "to":   { "node_id": "node-b", "team_id": "t-lab" },
  "trace": { "trace_id": "7b0e...", "parent_span": "2c8d...", "origin_node": "node-a" },
  "hops": 1,
  "task_id": "d41a...",
  "attempt": 1,
  "sig": { "alg": "ed25519", "key_id": "node-a@3", "value": "base64..." },
  "body": { "...": "类型相关,见 §4" }
}
```

### 3.3 身份与签名(v1 最小闭环)

完整身份与归属模型是纪要 §8.2 的主题,这里只定与信封咬合的最小集:

1. **签名**:每个节点入网时生成 Ed25519 密钥对;**所有业务消息(`task.*` 与 `rpc.*`)均由发送方私钥**对"头+body 的规范序列化(字段名字典序、UTF-8、不含 `sig`)"签名。**body 必签**——派单的内容就是 body,签头不签 body 防不了篡改任务;rpc 必签则让绕过网关的直连路径(§9 v1.5 局域网直连)在节点侧仍有完整防线。
2. **公钥分发**:注册中心兼任公钥目录,按 `(node_id, key_epoch)` 查询;验证方本地缓存。v1 采用 TOFU(首次使用信任),后续升级路径留给 §8.2 篇。
3. **传输层认证**:节点对中心(注册中心 API、通讯网关握手)使用注册中心自签的 node token(02 §3.2);信封签名解决的是**节点间的责任归属**,两者并存不互替。
4. **验证失败**:静默丢弃 + 本地审计事件;不回错误(不给探测者任何回声)。
5. `enc` 字段**预留未用**:端到端加密启用前,中心在技术上可读 body;协议上已按 P3 约束自己不去读。

## 4. 消息类型族

纪要 §7 的两种协同模式在此**塌缩为一族任务消息**:日常互助 = 单跳、无项目上下文、短租约的 `task.offer`;项目级协同 = 带 `project` 上下文的同一族消息。差别只在 offer 的字段取值,不在协议。唯一独立的是无副作用的问答(不占租约、不进状态机)。

### 4.1 rpc.* —— 问答(轻量、只读、无副作用)

| 类型 | 方向 | body 概要 |
|------|------|-----------|
| `rpc.ask` | → | `{request_id, question, context_ref?, timeout_ms}` |
| `rpc.answer` | ← | `{request_id?, answer, refs[]}`,`reply_to` 指向 ask |

超时即弃,可重发(新 `msg_id`,同 `request_id` 由被问方去重);**同样必签**(§3.3),验签失败静默丢弃——rpc 虽轻量,不豁免于身份体系。适用:问问题、查状态、探询能力。**凡"让对端做事"一律走 `task.*`,不借道 rpc。**

### 4.2 task.* —— 派单生命周期(互助与项目统一)

| 类型 | 方向 | 时机 | body 概要 |
|------|------|------|-----------|
| `task.offer` | 牵头→执行 | 派单/改派 | 见下 |
| `task.accept` | 执行→牵头 | 接单 | `{lease_ms(执行方确认值), started_at}` |
| `task.reject` | 执行→牵头 | 拒单(快速 NACK,§6 R6) | `{reason_code, retryable, retry_after_ms?, detail?}` |
| `task.progress` | 执行→牵头 | 周期心跳 | `{state, pct?, note?, logs_ref?}` —— 心跳即续租 |
| `task.result` | 执行→牵头 | 完成 | `{status:"done", summary, artifacts[], files[]}` |
| `task.fail` | 执行→牵头 | 失败 | `{reason_code, retryable, summary, diagnostics_ref}` |
| `task.cancel` | 牵头→执行 | 撤销 | `{reason: reclaim\|user\|project_aborted}` |
| `task.cancel.ack` | 执行→牵头 | 确认停止 | `{}`(若完成先于 cancel 到达,仍发 result 并标 `completed_before_cancel`) |

**`task.offer` body 字段**(本文最重要的一张表):

| 字段 | 必填 | 说明 |
|------|------|------|
| `kind` | ✅ | `aid`(日常互助)/ `project`(项目协同) |
| `summary` | ✅ | 人可读的任务描述(即给对端 LLM 的任务书正文) |
| `contract` | kind=project 必填 | **接口契约**:交付物定义、验收方式(如"跑 X 测试通过")、与图谱其他节点的接口约定。项目并行开发的语义冲突防线(纪要 §6 风险) |
| `required_caps` | — | 能力自评清单(如 `env:ios-sign`)。执行方不满足 → `reject(unsupported_caps)`,这是执行侧最快的一条 NACK 路径 |
| `workspace` | — | git 引用 `{repo, base_ref}`;协作落地选型留纪要 §8.4 |
| `deadline_ms` | — | 相对时限(P5),超期执行方应自行放弃并 `fail(deadline_exceeded)` |
| `lease_ms` | ✅ | 牵头方建议的租约时长;执行方在 accept 里可确认或下调 |
| `project` | kind=project | `{project_id, lead_node}`;图谱本身不上网,留在牵头方(§4.3) |
| `payload` / `payload_ref` | 二选一 | ≤`MAX_BODY_INLINE` 内联;超出用引用 `{ref_uri?, repo?, path?, sha256, size}`(§6 R10) |
| `requires` | — | 超出执行方默认执行档案的权限声明(网络出口/工具/确认级,→ 03 §6.1);执行方据此走本地人确认或拒绝,而非事后发现 |

### 4.3 项目图谱的归属

任务图谱(分工图、依赖边、状态)**只存在于牵头方的内存+本地持久化**,不上中心、不进消息。节点间只流动本节定义的消息;图谱靠 `task.progress/result/fail` 回流来更新。牵头方持久化检查点 + 任务幂等(§6 R1)使**新牵头者可凭检查点接管**(leader loss 的预案,详见 §12 开放问题)。

## 5. 派单生命周期

### 5.1 牵头方状态机(每个 `task_id` 一份)

```
              offer ──── accept ────▶ running ──── result ───▶ done ✅
  drafting ──▶
              └── reject ──┐
  offered ── offer_ttl 到期 ┤
                           ▼
                     改派判定(R7/R8)── attempt+1 ──▶ 重新 offer
                           │
  running ── fail ─────────┤(retryable?)
  running ── 租约超时 ──▶ reclaiming ── drain 窗口 ──┘(R4/R5)
  任一态 ── attempt > max_attempts ──▶ escalate ❌(交回上层/用户)
  任一态 ── 用户/上游取消 ──▶ cancelling ──▶ closed
```

### 5.2 执行方状态机

```
  offered ── accept ──▶ running ──▶ result_sent ✅
     │ reject(立拒,六选一 reason)──▶ 终态
     └ 本地 offer_ttl 过期 ──▶ reject(expired)
  running ── fail ──▶ fail_sent
  running ── 收到 cancel ──▶ 停止 ──▶ cancel.ack(或 §6 R5 赛跑)
```

### 5.3 正常时序

```
牵头方(设备A)                          执行方(设备B)
  │ task.offer(attempt=1, lease_ms=300s)    │
  │────────────────────────────────────────▶│ 自评 required_caps / 策略 / 负载
  │◀────────────────────────────────────────│ task.accept(lease_ms=300s)
  │            ◀──── task.progress(renew) 周期(≈lease/3)────▶ 执行中
  │◀────────────────────────────────────────│ task.result(artifacts 为引用)
  │ 校验、整合(lead 本地;图谱更新)
```

## 6. 可靠性规则(R1–R10)

> 以下规则是状态机的语义细则,实现时每条都应可追溯到测试用例。

- **R1 投递假设与幂等**:底层通道至少一次、不保序。所有 task.* 处理以 `(task_id, attempt, type)` 去重;重复 offer 幂等(已 accept 则忽略重投);重复 result 幂等(已 done 则忽略)。
- **R2 offer 有效期**:offer 携带相对 `offer_ttl_ms`;执行方收到时已过期 → 回 `reject(expired)`;牵头方本地计时,到期未 accept 视为 `rejected(expired)`,进改派判定。两者独立计时,互不依赖对钟。
- **R3 租约与心跳**:accept 时刻起租约 `lease_ms`;`task.progress` 即续租;心跳间隔 = `lease_ms/3`;牵头方**连续错过 2 个心跳 + 宽限 `grace_ms`** 判 lost。执行方崩溃、休眠、断网统一表现为停跳,不需要单独的失败探测协议。
- **R4 超时回收**:判 lost → 发 `task.cancel(reason=reclaim)` → 进入 **drain 窗口 `drain_ms`**:窗口内同 attempt 的 `result/fail` 仍接受(赛跑窗口,执行方可能恰好做完);窗口关闭即 attempt+1 改派。**先撤销、后改派**,顺序不可反。
- **R5 僵尸防护**:执行方发送 result 前自检——若已收到过 cancel、或本地租约已超时,不发 result,回 `cancel.ack`;若已完成但尚未交付时收到 cancel,仍发 result 并标 `completed_before_cancel`(赌赛跑窗口)。改派后迟到的旧 attempt 结果,牵头方按 attempt 不符**直接拒收**并回 `reject(stale_attempt)`(让白干的执行方知道,便于其记账/清理)。
- **R6 快速拒绝(NACK 优先)**:执行方不接受就必须立刻 `reject`,禁止沉默等超时。reason_code 初版枚举:`busy`(负载满)、`policy_denied`(信任/策略)、`unsupported_caps`(能力不符)、`unsupported_version`、`expired`、`refused_loop`(hops 超限)、`stale_attempt`、`other`。`retryable` 与 `retry_after_ms` 供牵头方改派决策。
- **R7 重试与升级**:attempt 超过 `max_attempts` → 终态 escalate,交回项目图谱/用户,不无限改派。
- **R8 改派约束**:改派目标排除最近一次失败节点(牵头方本地状态,不进信封);换目标不改 `task_id`,只增 `attempt`。
- **R9 广播禁令**:task.* 与 rpc.* 一对一;仅发现类消息(presence/能力)允许广播,广播不承载任务语义。
- **R10 负载内联上限**:body 超过 `MAX_BODY_INLINE` 必须走 `payload_ref`(`{ref_uri?/repo?, path?, sha256, size}`);执行方按 sha256 校验。引用解析方式(对象存储/git/直连拉取)是纪要 §8.4 的选型,信封只锁结构。

## 7. 委托链与环防护

每条"龙"都可转包,委托树无全局协调者,环防护必须在信封里:

1. `hops` 每转派 +1;收到 `hops > MAX_HOPS` 的 offer → `reject(refused_loop)`。默认 `MAX_HOPS = 8`。
2. `trace` 三元组(`trace_id/parent_span/origin_node`)原样透传,不得改写;执行方本地日志、进度消息均携带,使任一任务的跨机全链路可在一处还原。
3. 转派时,新任务的 `trace.parent_span` = 触发转派的那条上游消息 `msg_id`。

## 8. 版本与演进

- `v` 为主版本整数。**同主版本内:新增字段必须被旧实现忽略**;删字段、改语义、改必填性 → 升主版本。
- 收到不认识的 `type` → 回结构化 `reject(unsupported_version)`(带自身支持的版本区间),**禁止静默丢弃**——版本漂移要能被对方看见。
- 节点版本/能力协商经发现类消息完成,属纪要 §8.3,本文只约定报错的形状。

## 9. 传输绑定(v0 设计)

信封与语义传输无关(P2);承载它的是纪要 §3 三大基础设施中的**通讯服务器**——本项目自建的**通讯网关**,部署于 `qlong.qianji.io`:

- **连接**:节点 ⇄ 网关保持 ws 长连接;握手以 node token 认证(02 §3.2),token 失效即断开重认。
- **在线投递**:网关按信封头 `to.node_id` 直接推送;时效敏感消息(offer / progress / cancel)走此路径。
- **离线暂存**:目标节点不在线时,信封进入其**收件箱**(网关侧队列),重连即补投。暂存是网关的职责,正确性却不依赖它——每个信封自带相对有效期(如 `offer_ttl_ms`、`rpc.ask.timeout_ms`),端上按 R2 独立判过期;网关侧的过期清理只是回收存储的优化。
- **投递语义**:至少一次、不保序(P4);网关不解析 body(P3),只看头做 **from 钉扎**(02 §7 A0)、路由、ACL 与审计。
- **演进**:**局域网/同网段直连为 v1.5 里程碑**——身份与签名体系与传输无关(验签按公钥,不按通道),节点直投不削弱安全模型,只省中心转发;公网 NAT 打洞仍列为远期优化。网关始终是跨网保底路径与离线队列——"全经中心转发"(纪要 §3)在广域上成立,局域内不必。

| 消息 | 路径 |
|------|------|
| `task.offer`(目标在线) | 实时推送 |
| `task.offer`(目标离线) | **project 类**:收件箱暂存,上线补投(R2 兜底过期);**aid 类不暂存**——10s TTL 走暂存必是死信,目标离线即按不可达处理,牵头方立即改派 |
| `task.progress / result / fail / cancel` | 实时推送;节点瞬断则暂存 |
| `rpc.ask / rpc.answer` | 仅实时;对方离线即失败返回(问答无暂存价值) |

## 10. 默认参数表

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `offer_ttl_ms` | 60 000(aid:10 000) | 接单时限 |
| `lease_ms` | 300 000 | 单次租约;长任务靠心跳续 |
| 心跳间隔 | `lease_ms/3` | 连续错过 2 次判 lost |
| `grace_ms` | 30 000 | 判 lost 前的宽限 |
| `drain_ms` | 30 000 | 回收后的赛跑窗口 |
| `max_attempts` | 3 | 超过升级 |
| `MAX_HOPS` | 8 | 委托深度上限 |
| `MAX_BODY_INLINE` | 256 KB | 超出走 payload_ref |

原则:参数是配置,协议只锁**字段与语义**;offer 可携带覆盖值(如 `lease_ms`),默认值仅是实现缺省。
