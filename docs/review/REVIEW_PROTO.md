# 协议与接口设计师评审意见

> 评审对象：README.md、docs/QLONG_DESIGN_NOTES.md、docs/QLONG_DESIGN_01_MSG_PROTOCOL.md（下称 01）、docs/QLONG_DESIGN_02_REGISTRY_TRUST.md（下称 02）、docs/QLONG_DESIGN_03_CAPABILITY.md（下称 03）。
> 说明：任务指令所写 `QUNLONG_*` 文件名在磁盘上不存在，实际文件为 `QLONG_*`（与 README 链接一致），本次按实际文件评审。
> 视角边界：仅评审消息信封、类型族、签名与版本演进、跨文档接口（API 面/查询协议/匹配语义）的设计质量；架构取舍、安全模型全局、执行档案合理性等交由其他队友。

## 结论

**verdict：有条件通过。**

方向与骨架是对的（信封一次定死、四 ID 分工、相对时长、NACK 优先），不需要结构性返工；但存在 1 项 blocker 与 6 项 major，全部属于「下一版必须钉死、且应在双机纸面走查与任何实现开工之前完成」的规范缺口。**通过条件：PROTO-1（签名规范化）与 PROTO-2～7 必须在下一版修订中解决**，否则不同语言实现将各自发明规范化器与关联规则，联调即互不兼容。

## 摘要

01 篇的信封字段族、四 ID 幂等体系与租约状态机质量较高，但存在三处「被多处引用却无处声明/定义」的缺口（`offer_ttl_ms`、`task.fail.reason_code`、`reply_to` 逐类型规则），说明字段表尚未闭环。签名的规范序列化只有一句「字典序、UTF-8」，数字/转义/浮点的跨语言歧义会让 Ed25519 验签在异构实现间系统性失败，这是全协议的根基，建议直接采用 JCS（RFC 8785）。§8 版本演进与 `reject(unsupported_version)` 语义不自洽，「发现类消息」在类型族中不存在。02 §9 与 03 §4/§5 的接口存在鉴权主体未定义、PATCH 与整体替换冲突、`caps_rev` 语义稀释、错误形状/分页缺失四类不一致。03 §3.2 匹配语义「前缀匹配」与「精确到所写版本段」两处措辞按字面均会产生误判。

## 问题清单

### Blocker

#### PROTO-1 ｜ blocker ｜ 01 §3.3 / D11：签名的「规范序列化」不具备跨实现可操作性，验签根基悬空

**问题**：01 §3.3 规定对「头+body 的规范序列化（字段名字典序、UTF-8、不含 sig）」签名。这一句话不足以让 Go/JS/Python/Rust 各自实现出**字节级一致**的规范化输入：

- **数字**：`1` vs `1.0` vs `1e0` 如何写？各语言 JSON 序列化器默认输出不同（JS `JSON.stringify(1.0)==="1"`，Python 保留 `1.0`）；超过 2^53 的整数在 JS 下精度丢失。
- **浮点**：`0.1` 的最短往返表示各语言不一致，尾数差异直接导致签名不一致。
- **Unicode 与转义**：Python `json.dumps` 默认 `ensure_ascii=True` 输出 `\uXXXX`，JS/Go 默认输出原始 UTF-8；`/` 是否转义（PHP 惯例转义）、`\u2028/\u2029` 是否转义，均未约定。「UTF-8」只说了编码，没说转义策略。
- **结构**：嵌套对象是否递归排序、数组保序、空白必须为零，均未写明。
- **「不含 sig」歧义**：是剔除整个 `sig` 对象，还是仅剔除 `sig.value`（即 `alg`/`key_id` 是否被签名）？这决定算法替换攻击面，必须钉死。
- **连带**：02 §6.1 密钥轮换要求「当前私钥对请求签名」，HTTP 请求签名的规范化同样未定义。

按现状实现，跨实现验签会**成批系统性失败**，而 01 §3.3-4 的对策是「静默丢弃」——表现为大规模丢单且无回声，排障成本极高；各团队随后各自放松验签则是安全回归。修复必须在任何实现之前完成，否则每个实现内嵌自己的规范化器，事后对齐即返工。

**修改建议**：在 §3.3 增设「规范序列化」小节：**直接采用 JCS（RFC 8785）作为规范性引用**（它已精确规定 UTF-8、零空白、按 UTF-16 码元排序键名、ECMAScript 数字序列化、最小转义），并给出 2～3 组跨语言测试向量（含中文、浮点、大整数、嵌套对象）。明确签名输入的精确构成，推荐：`signature_input = JCS(envelope \ {sig})`（整对象剔除），密钥选择不依赖 `sig.key_id` 而依赖已被签名的 `from.key_epoch`（见 PROTO-12），算法混淆风险以「alg 白名单（v1 仅 ed25519）」兜底。02 §6.1 的请求签名指向同一 JCS 引用，并定义签名覆盖的请求要素（method/path/body 哈希/时间戳/nonce）。

### Major

#### PROTO-2 ｜ major ｜ 01 §4.2 offer body 字段表 vs §6 R2、§9、§10：`offer_ttl_ms` 被三处引用，却未在任何字段表中声明

**问题**：R2 说「offer 携带相对 `offer_ttl_ms`」；§9 离线暂存说「每个信封自带相对有效期（如 `offer_ttl_ms`、`rpc.ask.timeout_ms`）」；§10 参数表给出默认值（aid 10 000）。但 §3.1 信封字段表没有它，§4.2 自称「本文最重要的一张表」的 offer body 字段表也没有它。它到底在信封还是在 body？——这不仅是字段归属问题：**签名覆盖头+body，字段位置直接改变签名输入与网关可见性**（P3：中心只见头）。若按 §9 字面进信封，则 §3.1「信封全部字段一次定死」的承诺已被打破；若进 body，§9 的「信封自带」表述是错的。同类参照物 `lease_ms`、`rpc.ask.timeout_ms` 都在 body。

**修改建议**：在 §4.2 offer body 表补一行：`offer_ttl_ms`｜✅（或注「缺省取 §10 默认」）｜接单时限，执行方按 R2 独立判过期；aid 默认 10s、project 默认 60s。同时把 §9「每个信封自带相对有效期」改为「请求类消息在 body 携带相对有效期（`offer_ttl_ms`、`rpc.ask.timeout_ms`）」，消除「信封级字段」的误读。

#### PROTO-3 ｜ major ｜ 01 §8 与 §6 R6：版本演进规则与 `reject(unsupported_version)` 语义不自洽

**问题**：三点互相矛盾——(1) §8 演进规则只谈字段（新增字段可忽略；删/改语义/改必填升主版本），**对「同主版本内能否新增 type」只字未提**；(2) 「收到不认识的 type → 回 `reject(unsupported_version)`」——收到未知 type 不是版本问题，按码名它是版本不满足，语义错位；(3) 「带自身支持的版本区间」——`task.reject` body 形状为 `{reason_code, retryable, retry_after_ms?, detail?}`，**没有结构化字段承载版本区间**，塞进自由文本 `detail` 就丧失机器可读性，与「结构化 reject」的自我要求相悖。

**修改建议**：§8 补一条类型演进规则：「同主版本内允许新增 type；旧实现收到未知 type 按兼容性缺口报错」；reason_code 拆分：新增 `unsupported_type`（未知类型）与保留 `unsupported_version`（`v` 字段超出支持区间），各自语义写清；在 §4.2 task.reject body 中**现在就**增加可选字段 `supported_v:[min,max]`（v1 即定义，后续不必改形状），「版本区间」落在该字段而非 detail。

#### PROTO-4 ｜ major ｜ 01 §4.2/§6 R6/§5.2、03 §7：`task.fail.reason_code` 无枚举，`deadline_exceeded`、`env_missing` 为散落自造词；reject 枚举「所有权」也含混

**问题**：R6 给了 reject 的 8 个码，但 `task.fail` body 的 `reason_code` **全文没有任何枚举**；实际被使用的 `fail(deadline_exceeded)`（01 §4.2 deadline_ms 行）与 `env_missing`（03 §7 反馈闭环，出现两次）都是未登记的自造词。协议对失败语义的核心字段不做枚举与扩展规则，跨实现必然各造各的码，牵头方依赖 reason 分类的改派决策无法机器化。另外 §5.2 写「reject（立拒，六选一 reason）」，而 R6 列了 8 个码——两处对不上，说明码表没有单一出处。`env_missing` 与 `unsupported_caps` 的边界（接单期声明不符 vs 执行期发现缺失）也需一句话钉死，避免实现者混用。

**修改建议**：在 §4.2 或 §6 增设「reason_code 登记表」，按 消息×方向×阶段 列全：reject 码即 R6 现有 8 个（标注 `stale_attempt` 为牵头→执行方向，见 PROTO-9）；fail 初始枚举建议 `deadline_exceeded` / `caps_missing`（或保留 `env_missing` 但登记在册）/ `internal_error` / `cancelled_by_peer` / `other`，并写明三条元规则：未知码一律按 `other` 处理不得报错；私有扩展码用 `x-` 前缀；新增标准码按同主版本兼容演进。同时把 §5.2 的「六选一」改为「按 §6 R6 码表」。

#### PROTO-5 ｜ major ｜ 02 §9 vs §3.2/§1：两个鉴权主体未定义，「team 成员 token」与「owner」都不在凭证体系中

**问题**：§3.2 只定义了两类凭证：node token 与 Ed25519 密钥对。但 §9 API 表中 `/v1/teams/{id}/nodes` 与 `/v1/nodes/{id}/pubkey` 的鉴权写的是「**team 成员 token**」——该凭证在全文无定义（形态？签发？校验什么？）；`/v1/teams/{id}/enroll-tokens`、`revoke/suspend` 的鉴权写「**owner**」——owner 是产品账号（人），而 §1 明说「账号体系属产品侧，本文只定义团队信任域」，那么控制台/人调这些端点走什么认证，本文没有给出可实现答案。接口表的鉴权列是合同，两处主体悬空意味着这四个端点目前不可实现。

**修改建议**：前者直接改为「node token（注册中心校验其 `team_id = {id}` 且节点 active）」，与 §7 A1/P8 的同队可见模型一致，不引入第三种凭证；后者明确「owner 端点经产品侧用户会话（控制台）代持调用，其认证机制属产品侧、接口契约不在本篇范围」，在表中加注占位说明；或者为 owner 引入显式 owner token 概念并写入 §3.2——二选一，不能留白。

#### PROTO-6 ｜ major ｜ 02 §9 vs 03 §4：`PATCH /v1/nodes/me` 的部分更新语义与 03「整体替换」直接冲突，且自愈机制依赖替换语义

**问题**：02 §9 将 `/v1/nodes/me` 定义为 GET/PATCH「自查/更新(name、caps、load)」——PATCH 按 RFC 5789 是部分更新；03 §4 却规定「`PATCH /v1/nodes/me` 时携带**完整**静态标签集 + 负载快照；注册中心**整体替换**」。两种读法都能自圆其说，实现分叉不可避免。更实质的是：03 §7 的自愈闭环（「同一标签被多次命中 → 自动把该标签从静态档案**摘除**并重新上报」）**只有在整体替换语义下才成立**——若注册中心按合并（merge）处理数组，被摘除的标签永远删不掉，自愈机制静默失效。

**修改建议**：拆资源、定语义：caps 与 load 独立为子资源，`PUT /v1/nodes/me/caps`（全量替换，写明「以上报集合为准，未提及即删除」）+ `PUT /v1/nodes/me/load`（快照替换）；`PATCH /v1/nodes/me` 仅保留 name 等标量字段的部分更新。若坚持单端点 PATCH，则必须写明「采用 JSON Merge-Patch（RFC 7386），其中 caps 数组一律整体替换」。02 与 03 同步改。

#### PROTO-7 ｜ major ｜ 03 §3.2 匹配语义：「前缀匹配」按字面会误命中，「精确到所写版本段」未定义段比较规则；标签值字符集未定义

**问题**：三点歧义都落在派单正确性的核心函数上——
(1) 「无 `@` = **前缀匹配**」：按字面（字符串前缀）实现，offer `tool:node` 会命中节点档案 `tool:nodejs`、`tool:node-lts`。表格与括号注（「存在该能力即可」）暗示的意图显然是「同名能力、忽略 @ 版本段」，但措辞给了错误实现的口实。
(2) 「带 `@` = **精确到所写版本段**」：offer `tool:node@20` vs 节点 `tool:node@20.1` 匹配吗？「精确」暗示全串相等（不匹配），「到所写版本段」暗示逐段比较（大版本 20=20，匹配）。表格只有 @18 对 @20 的反例，正例缺失，两种实现都写得出来。
(3) 标签值字符集未定义（03 §3.1 只说「值小写」）：`:` 与 `@` 是结构保留字，值内能否出现、允许什么字符，直接关系匹配与 URL 编码（见 PROTO-8）。

注意：这不是要求提前做 03 §10 已声明的区间语法（`@>=18`），而是把**现有**规则的字面语义钉死。

**修改建议**：§3.2 改写规则：「无 @：类与值段必须完全相等（节点侧 `@版本` 段忽略），非字符串前缀匹配」；「带 @：按 offer 所写段数逐段比较，数字段按数值比较（offer 写 n 段则比较节点值前 n 段）」；补正例/反例行：`tool:node` vs `tool:nodejs` ❌、`tool:node@20` vs `tool:node@20.1` ✅、`env:python@3` vs `env:python@3.12` ✅；§3.1 补一句「值字符集：`[a-z0-9]` 加 `-`/`_`/`.`，`:` 与 `@` 为保留分隔符」。

### Minor

#### PROTO-8 ｜ minor ｜ 02 §9 / 03 §5：错误响应形状、分页、查询参数编码未定义

**问题**：03 §5 只给了 200 的响应形状。团队节点列表会增长，无分页约定（offset? cursor?）；4xx/5xx 的错误 body 结构与错误码命名空间（节点端要程序化处理 401/403/404/409）全文未定义；`?caps=env:ios-sign,tool:node@20` 用逗号分隔多值，值内含 `:`/`@`（合法但易被错误编码），是「逗号分隔单参数」还是「重复 `caps=` 参数」未约定。

**修改建议**：补一节「HTTP 约定」：错误 body 统一 `{error:{code, message, detail?}}`，code 用稳定字符串枚举（如 `team_mismatch`、`token_expired`）；列表返回 `{nodes:[...], next_cursor?}`，v1 可先规定「全量返回，字段预留」；caps 过滤规定为重复参数 `caps=env:ios-sign&caps=tool:node@20`，值按 RFC 3986 编码。

#### PROTO-9 ｜ minor ｜ 01 §4.2 vs §6 R5/§8：`task.reject` 声明方向为「执行→牵头」，但 R5 与 §8 都让对端回 reject，且「已知类型、意外方向」无处理规则

**问题**：§4.2 类型表定义 `task.reject` 方向为 执行→牵头（接单拒绝）；但 R5 要求**牵头方**对迟到旧 attempt 回 `reject(stale_attempt)`，§8 要求**任意接收方**对未知 type 回 `reject(unsupported_version)`——同一类型在文档内被双向使用，与类型表矛盾。且执行方状态机（§5.2）没有「收到 reject」的迁移，协议也没有「已知类型但从意外方向到达」的处理规则（丢弃？忽略？回错？），实现者只能各自猜测。

**修改建议**：二选一并写明：(a) 将 reject 扩为双向通知类型，§4.2 方向列改「双向」，并把「`stale_attempt` 仅牵头→执行、其余码仅执行→牵头」写进码表；(b) 保持 reject 单向，另设轻量 `error`（或 `task.nack`）双向通知类型承载 `stale_attempt`/`unsupported_version`。同时在 §6 补通用规则：「收到已知类型但方向/阶段不符 → 忽略 + 审计，不回错误」。

#### PROTO-10 ｜ minor ｜ 01 §3.1：`reply_to` 只有一句「应答类消息关联的请求 msg_id」，「应答类」未定义、逐类型规则缺失

**问题**：哪些类型是「应答类」？`rpc.answer` 明确指向 ask（§4.1），但 task.* 侧完全没说：accept/reject/第一次 progress/result/fail/cancel.ack 是否携带 `reply_to`、指向 offer 还是 cancel 的 `msg_id`？task.* 已有 `(task_id, attempt)` 作为逻辑关联主键，`reply_to` 与它的分工（消息级关联 vs 任务级关联）未说明。实现者只能各自决定：全带、不带、或改派后指向错误的 offer。

**修改建议**：在 §3.1 或 §4 加一张逐类型小表：`rpc.answer → ask.msg_id`；`task.accept/reject → 所应答 offer 的 msg_id`；`task.progress/result/fail → 对应 offer 的 msg_id`（改派后指向新 offer）；`task.cancel.ack → cancel 的 msg_id`；并注明「任务级关联一律以 `(task_id, attempt)` 为准，`reply_to` 仅消息级排障用，缺失不构成协议错误」。

#### PROTO-11 ｜ minor ｜ 01 §4.1：`rpc.answer` 的 `request_id` 标为可选，但应答方不可能没有它

**问题**：`rpc.ask` body 必含 `request_id`，answer 是对 ask 的直接应答，`request_id?` 的「?」没有成立场景；反而诱发实现者省略它、只按 `reply_to` 关联。而 §4.1 的重发规则是「重发用新 `msg_id`、同 `request_id`」——若被问方应答的是重发前的旧 ask，`reply_to` 指向旧 `msg_id`，提问方若只按 `reply_to` 匹配就会漏收/错配。

**修改建议**：`rpc.answer` body 改为 `{request_id, answer, refs[]}`（必填），并写一句「提问方按 `request_id` 关联应答，`reply_to` 仅辅助排障」。

#### PROTO-12 ｜ minor ｜ 01 §3.1/§3.3：`sig.key_id` 内嵌纪元与 `from.key_epoch` 构成双源，不一致时以谁为准未定义

**问题**：示例中 `sig.key_id = "node-a@3"` 与 `from.key_epoch = 3` 语义重叠。轮换窗口内两者可能不一致（实现 bug、部分升级、恶意构造），而 §3.3 规定查钥按 `(node_id, key_epoch)`——未规定冲突时信奉哪个字段。双源不一致是签名验证的第一类现实故障。

**修改建议**：规定「公钥查取一律以**签名过的** `from.key_epoch` 为准；`sig.key_id` 降级为诊断字段，建议实现直接由 `(from.node_id, from.key_epoch)` 派生而不单独传输」，或干脆从 `sig` 中删去 `key_id`、只留 `{alg, value}`——单一事实源。

#### PROTO-13 ｜ minor ｜ 01 §6 R9 / §8：「发现类消息」在类型族中不存在，§8 的版本协商指向已被 03 篇取代的机制

**问题**：R9 许可「仅发现类消息（presence/能力）允许广播」，但 §4 类型族只有 `rpc.*` 与 `task.*`，四份文档没有任何 `discovery.*`/`presence.*` 类型；网关也无从按头判定一条消息「属于发现类」——这是一条许可了不存在类别的规则。§8「节点版本/能力协商经发现类消息完成，属纪要 §8.3」同样失效：纪要 §8.3 的落地篇（03）实际用 REST 目录 + `rpc.ask` 兜底，02 §5.2 目录里也已有 `qlong_version` 字段，没有任何消息式协商。

**修改建议**：v1 明确写「**当前版本所有信封均一对一，无广播类型**；R9 的广播许可保留为未来发现类消息族的扩展位（届时须新增类型命名空间并同步修订 ACL）」。§8 的协商指引改为「版本可见性经 02 §5.2 目录字段（`platform`/`qlong_version`）与 03 §5 查询获得；`reject` 报错形状见本节」。

#### PROTO-14 ｜ minor ｜ 02 §5.2 vs 03 §4/§5：`caps_rev` 随每次动态刷新自增，从「能力档案修订号」退化为「上报计数器」

**问题**：03 §4 规定每次 PATCH（含默认 60s 一次的动态负载刷新）都「整体替换 + `caps_rev` 自增」。于是 `caps_rev` 每 60s 必变：以它做缓存失效键的牵头方每分钟全量拉新目录；想感知「静态能力是否变化」则必须全量 diff——修订号的核心价值（变更检测）归零。02 §5.2 对它的定位是「能力档案引用」，两篇的语义预期不一致。

**修改建议**：`caps_rev` 仅在**静态标签集变更**时自增；动态时效由负载快照自带的 `ts`/`ttl_ms`（03 §3.3，已存在）承担。03 §4 相应改写，02 §5.2 字段说明同步。

#### PROTO-15 ｜ minor ｜ 02 §6.1/§6.2/§5.2：密钥轮换后旧 epoch 公钥可查性未定义，在途/离线消息会被误判为不可验

**问题**：Node 表只存**当前** `pubkey/key_epoch`；§6.2 规定验证方查目录「查到不存在 → 负缓存（10 分钟）+ 拒签」。节点轮换（epoch N-1 → N）后，所有未缓存旧钥的对端在验证 in-flight 与收件箱补投的旧 epoch 消息时会查无此钥 → 负缓存 → 合法消息成批拒收，且持续 10 分钟。R1 的「至少一次」承诺在轮换场景被打穿。

**修改建议**：目录按 `(node_id, key_epoch)` 保留**历史公钥**（单调追加，至少保留最近 K 个或永久，供审计），「查无此 epoch」与「已吊销」返回不同错误码；负缓存仅适用于确认从未存在的 epoch。02 §6.2 补这段轮换窗口语义。

### Nit

#### PROTO-16 ｜ nit ｜ 01 §4.2/§3.1：两个字段的角色/初值未标注——`task.accept.started_at` 与 `trace.parent_span` 初值

**问题**：`task.accept` body 含 `started_at`（绝对时刻），与 P5「相对时长、`ts` 仅诊断」的关系未说明——是纯诊断还是参与租约逻辑？`trace` 三元组为必填，但发起消息（hops=0）的 `parent_span` 取什么值（null？省略？自指 msg_id？）未定义。

**修改建议**：`started_at` 标注「仅诊断，RFC3339，不参与任何过期/租约判断（P5）」；`trace.parent_span` 规定「发起消息取 `null`，转派时取上游 `msg_id`（§7.3）」。

#### PROTO-17 ｜ nit ｜ 01 §4.2 vs 03 §3.1/§3.2：`ios-sign` 标签的类归属跨文档漂移（`env:` vs `tool:`）

**问题**：03 §3.1 示例为 `tool:ios-sign`（并称其为团队约定组合能力），03 §3.2 匹配表与 01 §4.2 的 `required_caps` 示例却用 `env:ios-sign`。同书同例不同类，标签词汇表本就靠示例统一认知，示范作用减分。

**修改建议**：统一为 `tool:ios-sign`（组合能力归 tool 类更贴切），修 03 §3.2 表行与 01 §4.2 示例；或在 03 §3.1 加注「示例标签全书统一写法」。

## 亮点

1. **四 ID 分工表（01 §3.1）**：`trace_id / task_id / attempt / msg_id` 的粒度、生成方、用途一次钉死，`attempt` 兼作幂等键与僵尸防护键，用最少的机制覆盖了重投去重、改派隔离、迟到拒收三个问题——同类设计里少见的干净。
2. **P5 相对时长原则贯穿始终**：R2 双端各自计时互不依赖对钟、§9 把正确性放端上（信封自带 TTL）、网关过期清理仅作存储优化——「不依赖跨机时钟」从原则到规则到传输绑定三层自洽。
3. **02 §7 的 A0 from 钉扎 + rpc 必签组合**：对「自报 from 伪造跨队」与「rpc 无签名套情报」两条攻击路径的闭合论证，明确写出了「若无 A0 会怎样」的反事实推理；§10 威胁模型坦承同队互信的固有风险而不掩饰，是信任边界文档的诚实范本。
4. **03 §6.1 远端任务执行档案直面提示注入的「常规路径」属性**：「offer 可声明 `requires` 但永远不能放宽档案」的权限单向收窄，加上闸 3 的 `missing` 明细反哺改派（顺手关闭了 01 开放问题 5），跨篇接口意识好。

## 开放问题

1. **规范序列化最终定案**：是否采用 JCS（RFC 8785）？签名输入的精确字节构成（`sig` 整体剔除还是仅剔除 value？`alg` 是否入签？）——请给出定案与跨语言测试向量（对应 PROTO-1/12）。
2. **`offer_ttl_ms` 的归属与覆盖层级**：进 offer body 还是信封？aid/project 两档默认值之外，牵头方可否在 offer 覆盖、执行方可否用本地配置收窄上限（对应 PROTO-2）？
3. **`task.fail.reason_code` 初始枚举**：除 `deadline_exceeded`、`env_missing` 外，v1 至少还要哪些码（上游失败？被取消？内部错误？），未知码与私有扩展规则如何定（对应 PROTO-4）？
4. **同主版本内新增 type 的兼容策略与版本区间的承载字段**：`unsupported_type` 与 `unsupported_version` 是否分码？`supported_v` 字段现在定不定（对应 PROTO-3）？
5. **02 §9 四个端点的鉴权主体定案**：「team 成员 token」是否就是 node token + 归属校验？owner 端点在产品侧账号体系就绪前的过渡方案是什么（对应 PROTO-5）？
6. **`@` 版本段的比较语义**：逐段数值比较（offer @20 匹配节点 @20.1）还是全串相等？这决定 §3.2 正例反例表的最终形状（对应 PROTO-7；注意这与 03 §10 已声明的区间语法是两回事）。
