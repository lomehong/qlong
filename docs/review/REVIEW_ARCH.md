# 首席架构师评审意见(群龙 Qlong:纪要 + 01–03 篇)

> 评审对象:README.md、docs/QLONG_DESIGN_NOTES.md、docs/QLONG_DESIGN_01_MSG_PROTOCOL.md、docs/QLONG_DESIGN_02_REGISTRY_TRUST.md、docs/QLONG_DESIGN_03_CAPABILITY.md(注:实际文件名为 `QLONG_*`,非任务清单所写 `QUNLONG_*`,已按实际文件评审)。
> 评审视角:总体架构与原则一致性、基础设施面/任务面边界、状态机完备性、单机形态保留主张、图谱本地化与接管可行性、跨篇职责、演进口子、中心三服务可用性/扩展性。协议细节与安全攻防不在此铺开。

## 结论

**有条件通过。** 总体架构方向正确且自洽,「中心做服务、边缘做决策」在 01–03 篇中被一致贯彻,未发现中心越界做调度决策的暗门;无 blocker 级根本缺陷。但存在 3 个 major 级缺口——图谱本地独占与 leader 接管预案之间的内在矛盾、01 §5 状态机多处缺失转移、网关「无状态可横扩」的错误默认假设——必须在下一版设计单元(§8.4 文件协同 + 双机走查)之前或同场解决,否则双机端到端走查会踩到这些洞,造成返工。

## 摘要

五份文档的架构骨架是健康的:基础设施面(注册/通讯/分发)与任务面(节点自治调度)的边界在协议层(P3 中心只见头)、数据层(P11 注册中心不学任务语义)、查询层(P14/D20 只过滤不排序)三层投影一致。单机形态保留的主张在数据模型(02 §4.2 单机 team)与执行面(03 §6.1 仅约束远端任务)上成立。主要问题集中在三处:①01 §4.3「图谱只留牵头方本地」与 §12.3「换人接管」互相矛盾,跨机接管在当前设计下物理不可行,且缺少 attempt 单调源/双主防护;②01 §5 两个状态机有若干缺失转移(非可重试失败的终态、cancelling 竞态、cancel.ack 悬挂、验收失败归途等),无不可达状态但边界闭合性不足;③02 §12.4 把网关路由面当无状态设计,而网关实为在线权威 + 离线收件箱的双重有状态角色,横扩方案必须提前设计。另有若干协议表一致性小问题。

## 问题清单

### ARCH-1
- **严重度**:major
- **文档与位置**:01 篇 §4.3「项目图谱的归属」、§12 开放问题 3「Leader loss 接管协议」;关联纪要 §5 边界澄清、README §状态
- **问题**:§4.3 规定「任务图谱只存在于牵头方的内存+本地持久化,不上中心、不进消息」,而 §12.3 的接管预案是「新牵头者凭检查点 + 幂等重放接管……接管即**换人**续跑同一 task_id」。「换人」若指跨节点接管,则检查点必须离开原节点——与「不上中心、不进消息」直接矛盾,当前设计下跨机接管物理不可行(原节点硬件死亡 = 项目连同检查点一起丢失)。若只指同机进程重启,则文档没有明说,读者会按「跨机接管可行」理解,后面 §8.4/实现会按错误预期设计。此外接管还有两个未回答的架构问题:(a) `attempt` 是「牵头方递增」的单调纪元(01 §3.1),跨 lead 接管后单调源在哪、旧 lead 复活(网络分区恢复)与新 lead 并存时如何 fence、如何让位——双主会对同一 task_id 发出两条 attempt 链,执行方与网关都无法仲裁;(b) 谁有权触发接管(纪要 §5 说「首是任务的属性」),无任何授权/发现机制。
- **修改建议**:在 01 §4.3 明确写入接管边界:v1 的接管 = **同一物理节点上的进程重启 + 本地检查点重放**(与现有设计完全兼容,图谱不出节点);跨机接管列为显式开放问题,并给出与「图谱不上中心」原则兼容的候选口子——例如同 team 内指定的检查点备份节点(端到端加密兼容,不经过中心)、或用户手动导出/导入检查点。同时在 §12.3 补三条接管前置条件:检查点必须包含 attempt 高水位与在途 (task_id, attempt, 执行方) 清单;接管方必须将所有在途任务 attempt 提到高水位之上再重派(fence);旧 lead 恢复后凭 presence/检查点纪元检测让位,禁止双主。

### ARCH-2
- **严重度**:major
- **文档与位置**:01 篇 §5.1/§5.2 状态机、§6 R4/R5/R7、§4.2 消息类型表、§5.3 正常时序
- **问题**:逐一核对两个状态机:**无不可达状态**,但存在多处缺失转移,实现的边界场景会无所适从:
  1. **非可重试失败无终态**。§5.1 中 `fail(retryable?)` 只画了「→ 改派判定」一条出路;`retryable=false`(如 `policy_denied`、`unsupported_caps` 且无替代候选)应立即进入终态,而 R7 只定义了「attempt 超过 max_attempts → escalate」。按现文非可重试失败也要烧完 3 次 attempt 才升级,语义错误且浪费改派。
  2. **cancelling 态的竞态结果无转移**。R5 允许执行方「完成先于 cancel 到达仍发 result 并标 `completed_before_cancel`」,但 §5.1 图中 `cancelling` 只有 `──▶ closed`,没有 `result → done`、`fail → closed` 分支。
  3. **cancelling 无超时**。`task.cancel` 丢失或执行方长期离线时,`cancelling ──▶ closed` 的触发条件未定义,状态悬挂。
  4. **未经请求的 cancel.ack 无处理**。R5 规定执行方「本地租约已超时,不发 result,回 cancel.ack」——lead 从未发过 cancel,却在 running 态收到 cancel.ack;§5.1 没有 running + cancel.ack 的转移。同时执行方状态机(§5.2)也缺「本地租约超时 → 自终止」转移,该行为只存在于 R5 文字里。
  5. **验收失败无归途**。§5.3 时序里 lead「校验、整合」,offer.contract 定义了验收方式(§4.2),但 result 校验不通过时走什么转移、发什么消息,全文无定义——这是项目级协同的主路径之一,不是边角。
  6. **被超越 attempt 的迟到 accept/reject 未定义**。R5 只规定迟到旧 attempt 的 *result* 拒收;暂存 offer 被改派后,旧 attempt 的 accept/reject 迟到抵达(02 §8 离线暂存使这成为常态),lead 应静默忽略,需写入 R1/R5。
- **修改建议**:重画 §5.1/§5.2 为显式转移表(状态 × 事件 → 动作/次态),逐条补上上述 6 处;新增终态 `failed`(区别于 escalate:failed=任务判定不可成,escalate=重试预算耗尽交回上层);为 `cancelling` 定义 `cancel_timeout_ms`(到期即 closed,取消尽力而为);在 R7 补「`retryable=false` 立即终态」;验收失败建议复用 cancel(reason=reclaim)+ attempt+1 重做语义并在 R4 标注,或新增 lead→执行方的显式 `task.nack`,与 ARCH-4 一并定案。

### ARCH-3
- **严重度**:major
- **文档与位置**:02 篇 §12 开放问题 4「注册中心高可用」、§8 在线状态、§7 A1;01 篇 §9 传输绑定、§2 P2/P4
- **问题**:02 §12.4 的默认取向「网关路由面应保持**无状态**可横扩」不成立:同一文档 §8 已把**网关连接态定为在线权威**(连接表 = 有状态),01 §9/D12 又把**离线收件箱**交给网关(持久化队列 = 有状态)。ws 长连接 + 按 node_id 寻址的推送 + 离线补投,横扩必然要求跨实例共享连接表/信箱与 node_id→实例的一致路由(粘滞或发布订阅),这不是「保持无状态」能涵盖的,是必须提前设计的核心架构件。另一个真空:中心整体不可达时任务面的行为没有任何定义——P2 宣称「可靠性由 §6 规则在端上保证」,但 §6 规则全部以「消息已发出」为前提,节点侧没有本地 outbox、退避重发、以及「哪些功能在无中心时仍可用」的降级声明;跨网任务面在中心故障时整体停摆且无语义(进行中的租约如何表现、恢复后补投顺序)。
- **修改建议**:①把 02 §12.4 改写为如实的有状态横扩问题:给出规模目标(节点数/消息速率),并设计网关集群三件套——连接注册(如 Redis pub/sub 或 gossip)、node_id 分片路由、收件箱落持久存储(与 01 §12.6 收件箱配额/持久化同场定);②在 01 §6 增补 R11「节点侧发送队列」:发送失败入本地 outbox、指数退避、信封自带相对有效期故重发天然幂等(R2/R1 已兼容),并声明无中心时的降级面 = 单机 + 局域网直连(v1.5 后);③注册中心目录面(HA)已列为开放问题,不重复,但建议在其解法中明确网关对目录的缓存失效策略(见 ARCH-5)。

### ARCH-4
- **严重度**:minor
- **文档与位置**:01 篇 §4.2 消息类型表(`task.reject` 方向「执行→牵头」)vs §6 R5(「牵头方……回 `reject(stale_attempt)`」)
- **问题**:消息方向自相矛盾:`task.reject` 在类型表中定义为执行方→牵头方,但 R5 要求牵头方对迟到旧 attempt 结果「回 reject(stale_attempt)」——这是牵头方→执行方使用同一类型。实现者按类型表建方向校验会直接冲突;且「验收失败回执」(ARCH-2 第 5 点)也需要一个 lead→执行方的消息,现类型族没有。
- **修改建议**:二选一并写回 §4.2 类型表:`task.reject` 声明为双向类型(body 增加 `by` 字段区分),或新增 lead→执行方的 `task.nack`(覆盖 stale_attempt 与验收失败),保持 reject 的「拒单」语义纯净。

### ARCH-5
- **严重度**:minor
- **文档与位置**:02 篇 §7 A1(to.team_id 缺省目录反查「带缓存」)、§4.2(换队后「目录与网关 ACL 同步更新」)、§6.2(负缓存 TTL 10 分钟)、§8(online 权威在网关)
- **问题**:注册中心与网关存在双向运行时耦合但同步机制未定义:目录 API 的 `online` 字段来自网关连接态(故障半径耦合,虽然 P12 的「发现类只读降级缓存」部分覆盖);更关键的是 A1 依赖的目录归属缓存,在 `qlong join` 换队、suspend/revoke 后如何失效——「同步更新」只有一句话,若靠缓存 TTL 自然过期,则换队后存在旧 team 消息仍被放行的窗口,与「换队后旧 team 立即不可达」的承诺不符。
- **修改建议**:为目录引入单调版本号(directory epoch),join/revoke/suspend 时 bump 并主动推送(或网关写后读校验)到各网关实例;A1 缓存记录携带 epoch,落后即回源。把该机制写进 02 §7 或新增 §7.1「目录-网关一致性」,并在 §9 API 面注明网关为目录变更的订户。

### ARCH-6
- **严重度**:minor
- **文档与位置**:01 篇 §9 传输绑定表(aid 类 offer「目标离线即按不可达处理,牵头方**立即改派**」)
- **问题**:「立即改派」依赖一个未定义的信号——消息类型族(§4.2)中没有投递失败/不可达通知,ws 绑定的每消息回执语义也未定义;牵头方无从区分「已入收件箱」「离线拒收」「发送失败」。按现文只能等 offer_ttl(aid=10s)到期走 R2,「立即」二字无机制支撑。
- **修改建议**:在 §9 传输绑定中定义逐消息投递回执(accepted / stored / undeliverable),作为通讯服务器提供的「服务」而非调度输入(与 P3/P11 不冲突);或将措辞改为「aid 类目标离线即 undeliverable,牵头方按 R2 兜底在 offer_ttl 到期改派」,承认 10s 上限。

### ARCH-7
- **严重度**:minor
- **文档与位置**:01 篇 §4.2 offer body 字段表、§4.2 task.progress body、§6 R6;03 篇 §7
- **问题**:字段卫生三处:①R2/§10 都依赖 offer「携带相对 `offer_ttl_ms`」,但 §4.2 自称「本文最重要的一张表」的 offer body 字段表中没有该字段;②`task.progress` body 的 `state` 取值枚举全文未定义;③R6 只枚举了 reject 的 reason_code,`task.fail` 的 reason_code 无登记处(03 §7 引入的 `env_missing` 无家可归);④`task.accept` 的 `started_at` 若为绝对时刻,与 P5「不依赖跨机时钟、ts 仅诊断」的关系需一句话声明。
- **修改建议**:offer 表补 `offer_ttl_ms`(必填);为 progress.state 给出最小枚举(如 `starting/working/finalizing`)或改为可选自由文本;在 01 §4.2 或附录增加 fail reason_code 登记表(env_missing 作为首条由 03 §7 回填);started_at 标注「仅诊断,同 ts」。

### ARCH-8
- **严重度**:minor
- **文档与位置**:01 篇 §3.3 第 5 点(enc 预留未用)、§8 版本与演进、原则 P1
- **问题**:E2E 加密的口子留了 `enc` 字段,但**签名与加密的次序未预留结论**:enc 启用后 `sig` 覆盖明文 body 还是密文,决定规范序列化规则、以及 P3「中心只见头」在加密时代的实际边界(若 sig 覆盖明文,验签方需先解密,中心审计语义也变)。P1 要求信封一次定死,此项属于「现在一句话、将来免返工」的决策,01 §8 演进节应钉住,不宜留到加密真正启用时。
- **修改建议**:在 §3.3 或 §8 增补一句原则性决策:enc 启用时采用 sign-then-encrypt(sig 覆盖明文,随密文同传),接收方解密后验签;网关可见面不变(仅头)。细节可留待加密篇,但次序结论现在写下。

## 亮点

1. **「笨中心」的全栈一致投影**:P3(中心只见头)→ P11(注册中心不学任务语义)→ P14/D20(查询只过滤、不排序不打分),原则在协议、数据、查询三层相互印证;通读 01–03 未发现任何中心越界做调度决策的机制,基础设施面/任务面边界是五份文档中最扎实的部分。
2. **信任模型闭环且演进口子齐备**:双身份(P9 通行证/身份分离)+ 双重执法(P10)+ A0 from 钉扎堵死自报身份的跨队伪造路径;P8 干净解决了「入网开放 vs 协同需归属」的纪要级张力;跨团队 grant(`to.team_id` 已预留)、E2E(`enc`)、LAN 直连(验签按公钥不按通道)均不需动信封即可演进——这正是 02 §12/03 §8 把 grant/能力可见性联动预留的价值。
3. **03 §6.1 远端任务执行档案是全套设计中最有价值的安全决策**:直面「LLM 任务书注入是常规路径固有属性」这一本质风险,默认低权档案、`requires` 只能声明不能放宽(收窄权在执行方)、本地人确认兜底,并在 02 §10 威胁模型中如实列出「同队机器被攻陷无解」的模型前提——不假装问题已解决,是诚实且可落地的责任划分。
4. **四 ID 分工(01 §3.1)+ 租约制 + 相对时长 P5**:trace/task/attempt/msg 粒度与归属清晰,幂等、僵尸防护、赛跑窗口、改派排除(R8)构成自洽的可靠性体系,R1–R10 可直接映射为测试用例;P5 从根上消除跨机时钟依赖,是协议长期正确性的关键决策。

## 开放问题

1. **Leader 接管的边界必须先答**:v1 是否明确「接管 = 同机进程重启」?若要跨机,检查点如何离开原节点、attempt 单调源与旧 lead 复活让位规则是什么?(对应 ARCH-1,阻塞 §8.4 双机走查的剧本设计)
2. **网关集群化的规模与形态**:预期节点规模与消息速率?在线连接表与离线收件箱用什么共享存储、node_id 如何路由到持有连接的实例?(对应 ARCH-3,决定 01 §9 绑定的可实现性)
3. **中心不可达时的任务面语义**:节点本地 outbox/退避是否纳入 v1?进行中租约在中心故障期间的表现(继续跑完?冻结?)与恢复后补投顺序是什么?
4. **验收失败的生命周期归途**:result 与 offer.contract 不符时,是复用 cancel+attempt+1 重做,还是需要独立语义?这与 ARCH-2/ARCH-4 是同一个决策,应在双机走查前定案。
