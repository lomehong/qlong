# 群龙(Qlong)评审意见 —— 产品与开发者体验

> 评审对象:README.md、docs/QLONG_DESIGN_NOTES.md(纪要)、QLONG_DESIGN_01_MSG_PROTOCOL.md(01 篇)、QLONG_DESIGN_02_REGISTRY_TRUST.md(02 篇)、QLONG_DESIGN_03_CAPABILITY.md(03 篇)。
> 说明:磁盘上实际文件名为 `QLONG_*.md` 前缀(本评审按实际文件引用;仓库内部链接自洽,无断链)。
> 视角声明:本文仅覆盖入网与使用旅程、owner 操作面、任务书可用性、可观测/可归因的产品缺口与命名一致性;协议安全、数据模型正确性等交由其他视角评审。

## 结论

**有条件通过。** 架构与协议层(01–03 篇)质量扎实,但「用户从哪进来、卡住了找谁、放弃时看到什么」这层产品旅程是当前五份文档中最薄的一层:入网主路径仅有 Unix 形态示例、enrollment token 的 TTL 与消费时点经不起真实操作链路推敲、owner 操作面(签发/暂停/吊销)没有任何篇目认领其归属、给对端 LLM 的任务书缺少结构与验收位。条件:六条 major 在 §8.4 双机纸面走查与 §8.5 分发安装器设计启动前处理完毕;minor 可随对应篇目顺带修订。

## 摘要

这套设计的开发者体验底子是好的:D5「零手工配置」配上了登录态继承归属与未登录先装后认领的双路径,拒绝路径(NACK 优先 + 五道闸 + missing 明细)把失败当一等公民设计,03 §6.1 远端执行档案对「任务书即注入面」的坦诚在同类设计里罕见。但入网旅程存在系统性缺口:02 §4.1 的安装示例是 Unix-only,而纪要 §4 承诺的是「任何可联网的设备」;5 分钟 token TTL 与未定义的 consumed 时点会让真实装机频繁失败且无出路;owner 的 suspend/revoke 是信任模型的最后防线,其控制台却在六份待设计清单里无家可归。另外三条可观测性缺口(网关 ACL 拒绝对诚实节点不可见、escalate 后用户面缺失、能力自愈静默改写)会让「无首而治」在实际运营中变成「出了事没人知道为什么」。以下 11 条按严重度排序。

## 问题清单

### DEUX-1 【major】`/install` 到在线的旅程在 Windows 下不成立,「装完即在线」的自启/服务化承诺无人认领

**文档与位置**:纪要 §4(「任何可联网的设备访问 https://qlong.qianji.io/install」「装完即在线」、D5)、02 §4.1(`curl …/install.sh | sh -s -- --enroll <token>`)、纪要 §8.5 / README「状态」(分发安装器排在 §8.4、§8.6 之后)。

**问题与依据**:①02 §4.1 唯一给出的安装形态是 `curl | sh`,Windows——恰恰是目标用户占比最高的开发平台——没有 `sh`,等效形态(`irm …/install.ps1 | iex`、winget/MSI)未提;纪要 §4「任何可联网的设备」的承诺与 02 给出的示例直接矛盾。②Windows 服务的安装必然触及提权决策(每用户安装 vs 全机服务)与防火墙首连提示(v1.5 局域网直连还需要入站规则),这两步是「零手工配置」最容易被击穿的地方,纪要 §8.5 的范围描述(「平台适配、安装脚本、自动注册的凭证下发流程」)没有点名它们。③「装完即在线」隐含「重启后自动在线」,即开机自启/守护进程服务化(Windows 服务、macOS LaunchDaemon、Linux systemd unit),这一关键产品属性在五份文档中零认领——若 §8.5 设计时才发现要回头改 02 的 enroll 时序与凭证落盘位置,就是返工。

**修改建议**:①在纪要 §8.5 条目中显式列出平台矩阵范围:安装方式(per-user / per-machine)、提权模型、自启与服务化方案、防火墙指引、卸载与凭证清除;首版建议 Windows + macOS + Linux 三平台纸面定稿后再写代码。②把「装完即在线」拆成可验收清单写进 02 §4 或纪要 §4:安装完成 → 守护进程自启 → ws 握手成功 → `/v1/teams/{id}/nodes` 可见 online=true;「重启后自动在线」作为同一清单的第二行。③02 §4.1 的示例命令标注「Unix 示例」并给 PowerShell 等效命令占位,避免读者以为这是跨平台规范。

### DEUX-2 【major】enrollment token 5 分钟 TTL 短于真实操作链路,consumed 时点与失败出路未定义

**文档与位置**:02 §4.3(TTL 5 分钟、单次使用)、02 §5.3(`used_by`/`consumed_at`)、02 §10(威胁表「enrollment token 重放」行)。

**问题与依据**:①真实链路是:打开 /install 页面 → 登录 → 生成 token → 复制整条命令 → 切到目标机器粘贴 → 下载安装包 → 安装 → `POST /v1/enroll`。新机器上「下载安装包 + 安装」一项就常超 5 分钟(慢网、大包、企业代理),§4.2 的认领路径更糟:owner 在控制台生成 token 后要把它搬到另一台物理机上,5 分钟几乎注定过期。②consumed 时点未定义:是 enroll 请求受理即烧掉,还是 enroll 成功才原子落定?若安装中途网络断开 token 已被记 `used_by`,用户重跑同一命令只会反复失败,且文档没有给出「token 过期/已用」时安装器应该输出什么。③失败出路缺失:enroll 失败后节点已装好但未入网,用户下一步做什么(刷新页面重新生成?原命令可否重试?)无任何约定。④5 分钟这一默认值被 02 §10 直接引用为重放缓解手段,说明它是安全参数——安全×体验的权衡应当显式论证,而非拍脑袋默认。

**修改建议**:①TTL 分场景:/install 页面随命令生成时建议默认 30–60 分钟(仍单次使用,重放窗口可控,且 token 权限仅 enroll、损失有界);控制台手工签发支持配置;在 02 §10 威胁表同步更新重放窗口论证。②钉死 consumed 时点:`consumed_at` 仅在 enroll 成功响应时原子写入;受理中的重复提交按幂等处理(返回同一凭据或明确 409 + `token_in_flight`),禁止「请求到了就算用掉」。③给安装器规定错误呈现契约:对 `token_expired / token_used / token_invalid` 输出人话(「邀请码已过期,请回到 /install 页面重新生成,重跑同一安装命令即可」),并附重新生成入口的深链。

### DEUX-3 【major】owner 操作面(签发 token、suspend、revoke)被多处依赖,但控制台与 owner 凭证没有任何篇目认领

**文档与位置**:02 §3.1(「账号体系……属产品侧」)、02 §4.3(签发人:team owner,经控制台)、02 §5.2 / §6.1(owner 手动暂停/恢复/吊销)、02 §9(鉴权列出现「owner」与「team 成员 token」)、纪要 §8 待设计清单(第 1–6 项无一覆盖 owner 面)。

**问题与依据**:02 的信任闭环里,「人」这一层只被引用、从未被设计:设备丢失恢复(§6.1)的第一步是 owner 去 suspend——在哪个界面点?用什么身份登录?§9 API 表的鉴权列直接写「owner」「team 成员 token」,而这两种凭证(用户侧凭证、团队查询凭证)在 02 §3.2 只定义了 node token,前者从未定义。控制台(成员列表、在线态、签发/撤销邀请、suspend/revoke、审计查看)是这套系统唯一的人工操作面,但纪要 §8 六个待设计项没有一项归它——按当前排序它最后一次被设计的机会在 §8.5 里,甚至不在清单上。这不是「以后补 UI」的问题:§6.1 的设备丢失 runbook 在控制台存在之前根本无法执行。

**修改建议**:①纪要 §8 增补第 7 项「owner 控制台与账号体系(最小面)」,或在 §8.5 中显式扩入;给出 v1 最小范围:登录 → 团队成员列表(在线态/版本/状态)→ 签发/撤销 enroll token → suspend/resume/revoke → 审计事件只读。②明确定义「owner」「team 成员 token」的凭证形态(浏览器会话?用户 PAT?),或明确宣布 v1 以 API-only 起步并给出等价操作路径——无论如何,02 §9 不应引用未定义的鉴权类型。③与 02 §12.5(多人共管审批流)划清边界:v1 最小面只做单 owner 操作,多人共管仍留开放问题。

### DEUX-4 【major】`task.offer` 的 summary/contract 作为「给对端 LLM 的任务书」不可用:contract 自由文本、aid 无验收位、result 无校验依据

**文档与位置**:01 §4.2(`summary`「即给对端 LLM 的任务书正文」;`contract` 仅 kind=project 必填、自由文本「验收方式(如"跑 X 测试通过")」)、01 §5.3(牵头方「校验、整合」)、纪要 §6(contract 是「项目并行开发的语义冲突防线」)。

**问题与依据**:全系统最高频的交互物是这份任务书,但它只有两个字段且都是自由文本:①aid 类任务完全没有验收位——执行方 LLM 拿到一段散文,牵头方收到 result 里的 `summary/artifacts/files` 后「校验」什么?没有判据,互助任务的质量闸门就是 vibes;②contract 虽被纪要 §6 寄予「语义冲突防线」的重任,却允许 LLM 写一句「跑 X 测试通过」了事,由对端 LLM 自由解释,防线的强度取决于文风而非结构;③任务书写得越散,03 §6.1 的注入面越大——结构化本身就在缩小「写歪」的空间。需说明:本条与 01 §12.7(已自我承认)不重复——§12.7 讲任务书如何**实例化为本地会话**(执行落地),本条讲任务书本身的**内容结构**(交互契约)。

**修改建议**:①将 `contract` 结构化为 `{deliverables:[{path|artifact, desc}], acceptance:[{check, machine_checkable?}]}`,project 必填、aid 选填但强烈推荐(执行方五道闸与牵头方校验都吃这个结构)。②在 01(或 §8.4 双机走查同场)给出任务书写作规范模板:目标、边界与禁止动作、完成判据、上下文引用——这同时是 03 §6.1 注入防线的第一道工程化措施。③`task.result` 增加 `acceptance_results[]`(逐条回填 acceptance 的通过情况),让「校验、整合」有依据,也让人审阅 result 时不用读散文。

### DEUX-5 【major】`requires` 字段两篇互相指认、无一篇定义;人工审批没有语义位

**文档与位置**:01 §4.2(`requires`「超出执行方默认执行档案的权限声明(网络出口/工具/确认级,→ 03 §6.1)」)、03 §6.1(「offer 只能*声明*需要什么(`requires` 字段)」、闸 5「转本地人确认后放行」)。

**问题与依据**:01 说结构看 03,03 说字段见 01——两处互相引用,实际没有任何一篇定义 `requires` 的形态(枚举?`类:值`?自由文本?)。这直接卡死两件事:①03 §6.1 执行档案的闸 5 与「越界拒绝」逻辑没有可解析的输入;②「敏感操作需本地人确认」(03 §6.1 表格最后一行)没有语义位——确认弹窗渲染什么?谁负责向本地用户解释「为什么一个远端任务要读我的 SSH key」?如果没有一个面向人的、任务发起方必须填写的解释字段,本地确认就退化成「看不懂就拒绝」或「看不懂也敢点允许」,后者比没有确认更危险。

**修改建议**:①在 03 篇(或 01 修订版)定义 `requires = [{class: tool|net|confirm, value, reason}]`,`reason` 必填且面向本地人写(人话,不是给 LLM 的);未知 class 照 03 §3.1 的向前兼容原则处理。②规定本地确认提示的渲染契约:任务来源(node/team、链路深度)+ summary 摘要 + `requires[].reason` + 将越界的档案维度列表;模板由执行方本地持有,发起方只供料。③「确认级」允许 offer 显式请求,但执行方档案保留最终否决权(与 P13 一致,03 §6.1 已有此原则,需在字段语义里重申)。

### DEUX-6 【major】网关 ACL 拒绝对诚实发送方完全不可见,归因丢失、白烧 attempt——与 01 §8 自己的可见性原则相抵触

**文档与位置**:02 §7 A0/A1/A2(拒绝路由 + 审计,未规定任何向发送方的回执)、A4(验签失败静默丢弃,反探测——此为有意设计,本条不挑战它)、01 §8(「版本漂移要能被对方看见」「禁止静默丢弃」)、01 R2/R4(offer_ttl 到期 → 改派 attempt+1)。

**问题与依据**:文档区分了两种静默的理由:对未认证探测者静默是反探测,正确。但 A0/A1/A2 拦下的是**已通过连接认证的诚实节点**的消息——例如 owner 对某节点执行 suspend(疑似失窃)后:该节点的 ws 连接未必被主动断开(02 §6.1 只说「网关停路由」),它继续干活,发出去的 `task.result/progress` 全部无声消失;各牵头方只会看到「对端停跳/超时」,按 R4 走回收、attempt+1、改派、直到 escalate——把一个「已被管理员暂停」的事实,错误归因为「节点不稳定」,并烧光 3 次 attempt。01 §8 对版本错误明确要求「必须被对方看见」,却任由策略拒绝完全不可见,两处哲学不一致。诊断场景同理:用户问「为什么我的机器收不到派单」,系统给不出任何信号。

**修改建议**:①suspend/revoke 时网关**主动断开**该节点现有连接并带语义 close code(如 4001 suspended / 4002 revoked),节点本地呈现「本机已被团队 owner 暂停,请联系 owner」——复用现有连接做反馈信道,不新增任何探测面,不破坏反探测原则。②对 A1/A2 这类已认证发送方的消息级拒绝,允许网关向**发送方本人**回送结构化路由拒绝(`routing.denied {rule, reason_code}`);未认证/伪造场景维持静默不变。③牵头方状态机区分「对端失联」与「被拒收」两类失败计数,避免前者烧 attempt。审计事件(02 已有)同步向 owner 控制台透出(DEUX-3 的最小面),形成双边可见。

### DEUX-7 【minor】未登录单机 team 的 `owner_user_id` 悬空,孤儿 team 无清理策略,`qlong join` 的过户语义缺在途义务处理

**文档与位置**:02 §4.2(未登录创建单机 team、`qlong join` 换队)、02 §5.1(Team.`owner_user_id`「产品账号引用」,未标可空)。

**问题与依据**:①单机 team 的成员只有节点自己、没有人类 owner,但 §5.1 的 `owner_user_id` 是产品账号引用——它指向什么?schema 未说可空,实现时必然各写各的。②节点 `join` 走后,旧单机 team 变成零成员孤儿,注册中心按现设计会永久累积;而仍有一台成员机的单机 team 又不能清(team_id 是该机的信任域)——两类「孤儿」需要区分对待,文档未提。③「收养/过户」语义不完整:`qlong join` 保留 node_id(过户的是节点,这点是清楚的),但 join 的前置条件未定义——若节点正作为执行方持有旧 team 的租约、或收件箱有未消费 offer,换队即让旧 team 牵头方只能等超时回收,新 team 立即可派单,边界行为悬空。

**修改建议**:①`owner_user_id` 明确可空;Team 增加派生状态(`orphan` / `active` / `self-owned`),写明:被换队遗留的零成员 team 按 GC 策略清除(如 30 天),活跃单机 team 保留并标注(它就是那台机器的信任域,清了会让节点 team_id 悬空)。②`qlong join` 增加前置检查:存在在途远端租约或未消费 offer 时要求显式确认;join 成功输出提示「旧 team 的牵头方将按租约超时回收你的任务」。③在 §4.2 用一句话钉死收养语义:「join = 节点过户(node_id/密钥/历史保留),team 不迁移」。

### DEUX-8 【minor】escalate 之后用户看到什么:终态事件无载荷定义、无落地面

**文档与位置**:01 §5.1 状态机(「attempt > max_attempts ──▶ escalate ❌(交回上层/用户)」)、01 R7(「终态 escalate,交回项目图谱/用户」)。

**问题与依据**:整套可靠性机制的出口是 escalate,但它是全文唯一没有 body 定义的终态:用户在哪看到(本地会话?通知?控制台?)、看到什么(试过哪些节点、各自为什么失败、有没有可行动的建议)、多跳链路中逐层上交时各次 attempt 的 `reject.reason_code / missing` / `fail.summary` 如何聚合,均无约定。对用户而言,「自治系统放弃时的交代」就是这个产品的售后体验——恰恰是 R6「拒绝即反馈」全部积累的信息最容易在这里被丢掉。

**修改建议**:①01 §4.2 定义 escalate 事件最小载荷:`{task_id, trace_id, attempts:[{node, outcome, reason_code, missing?|summary?}], final_reason, diagnostics_ref}`(新增可选字段,不破坏 v1)。②规定用户面呈现规范(可写进纪要或未来产品篇):本地会话卡片四要素——托了什么事、试过谁、为何放弃、建议动作(如「为 node-b 安装 `tool:ios-sign` 后重试」)。③建议赶在双机纸面走查前定稿,走查正好能验证这条链路。

### DEUX-9 【minor】03 §7 自愈摘标签是静默改写:无本地可见性、无恢复路径、存在误伤归因

**文档与位置**:03 §7(「同一标签被多次 env_missing 命中(阈值本地定),群龙自动把该标签从静态档案摘除并触发上报」)、03 §4(静态变更上报)。

**问题与依据**:①静默:节点对外宣传的能力被程序自行修改,本机用户不知情、team 内无人知情、无审计痕迹——与 P13「声明可以过期、拒绝不会」的坦诚气质相悖:自愈让声明**看起来**永远准,反而掩盖了漂移的发生。②无恢复路径:标签摘了,之后用户装好了工具/修好了环境,谁把它加回来?§4 的「静态变更检测到即上报」能否覆盖自愈摘除后的重加,未说明;存在摘除↔重加的抖动循环风险(每次翻转都 bump `caps_rev`)。③误伤归因:`env_missing` 可能是牵头方的需求写错(要了不该要的标签),执行方却据此自断真实能力,且牵头方本地「节点-能力记忆」(降权/拉黑)同步被污染,两处状态互相打架。④阈值「本地定」连默认值都没有。

**修改建议**:①摘除动作本地必现:`qlong caps` 可查 + 本地通知/日志一条(「因连续失败已暂停声明 tool:ios-sign」)。②摘除用 `suppressed` 标记而非删除;恢复走既有静态检测或周期低成本自检,抖动加滞回(如恢复后 24h 内不再自动摘)。③给默认阈值(如 24h 内 ≥3 次同类 `env_missing`),并区分「声明失真」与「需求错误」:仅当多个不同牵头方重复命中时才自动摘,单一来源重复失败只做牵头方侧降权、不摘标签(或摘标签需本地人确认)。

### DEUX-10 【minor】待写篇目排序:§8.5(分发安装器)排在最后,而它是全部用户旅程的入口、且其关键参数已被 02 冻结

**文档与位置**:纪要 §8 评审注记 + README「状态」(顺序:§8.4 文件协同 + 双机纸面走查 → §8.6 离线弱网 → §8.5 分发安装器)。

## 亮点

1. **入网双路径的产品设计(02 §4.1/§4.2,D14)**:登录态经一次性 token 继承归属保住 D5「零手工配置」,未登录则先装成合格单机、事后 `qlong join` 认领——渐进式 onboarding 给了用户零摩擦的第一次体验,又给信任归属留了清晰的落点,这是同类系统里少见的好设计(其 token TTL 缺陷见 DEUX-2,属参数问题而非结构问题)。
2. **远端任务执行档案(03 §6.1,D22)**:直面「任务书即注入面、无需任何人被攻陷」这一常规路径固有风险,给出默认低权档案 + `requires` 只声明不放宽 + 本地人确认兜底的三层结构,并如实声明「缩窄爆炸半径,不假装消除」——产品诚实度是安全沟通的范本。
3. **拒绝被当作一等公民(01 R6、03 §6 五道闸)**:禁止沉默等超时、拒单六选一 reason_code、能力不符回 `missing` 明细反哺改派(顺手关闭了 01 开放问题 5)——失败路径的可归因性设计贯穿两篇,是派单系统能被运营的前提。
4. **参数外置与演进纪律(01 §8/§10)**:协议只锁字段与语义、默认参数是配置;版本漂移「禁止静默丢弃」。这让 01–03 篇在落地时具备被实现、被测试、被演进的开发者友好性。
