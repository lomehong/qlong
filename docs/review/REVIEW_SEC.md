# 安全工程师评审意见 —— 群龙(Qlong)设计文档 01–03 篇初稿

> 评审对象:README.md、docs/QLONG_DESIGN_NOTES.md、docs/QLONG_DESIGN_01_MSG_PROTOCOL.md、docs/QLONG_DESIGN_02_REGISTRY_TRUST.md、docs/QLONG_DESIGN_03_CAPABILITY.md。
> 说明:任务清单中的 `QUNLONG_*` 文件名在仓库中不存在,实际文件为 `QLONG_*` 前缀,本评审以实际文件内容为准。下文引用格式:01=QLONG_DESIGN_01_MSG_PROTOCOL.md,02=QLONG_DESIGN_02_REGISTRY_TRUST.md,03=QLONG_DESIGN_03_CAPABILITY.md,纪要=QLONG_DESIGN_NOTES.md。

## 结论

**verdict:需重大修订**

核心理由:存在一项 blocker——消息级重放防护完全缺失,而新鲜性字段按 01 篇自己的 P1 原则属于「v1 信封一次定死」的范畴,事后补即重大返工;同时跨队隔离这一核心安全不变式(02 §7「零可达,且两条路径都闭合」)在 A1 现行表述下存在可绕过路径。其余 major 项集中在信任锚(TOFU 定性)、密钥生命周期(旧纪元签名)与供应链(install 管道、开放注册滥用),均需下一版集中处理。

## 摘要

01–03 篇的安全设计意识整体高于平均水准:A0 from 钉扎、rpc 全量签名、双重身份/双重执法(P9/P10)、远端任务执行档案(03 §6.1)构成扎实骨架,威胁模型如实声明「团队内攻陷无解」等模型前提,值得肯定。但威胁模型存在系统性遗漏:消息级重放仅覆盖 enrollment token 一处,网关作恶的具体后果、install 管道供应链、开放注册滥用均未入表。跨队隔离在 A1 规则下可被伪造 `to.team_id` 穿透网关,仅靠节点侧 A5 兜底且产生回声 oracle,「零可达」论断不成立。TOFU 的实际信任锚是注册中心目录(每次缓存未命中回源)而非 ssh 式首连钉扎,现有定性低估了目录被攻陷的后果。建议修复顺序:SEC-1(信封新鲜性)→ SEC-2/SEC-3(网关锚定与回声边界)→ 生命周期与供应链各项。

## 问题清单

### SEC-1 · blocker · 消息级重放无任何防护,且 P5 相对时长使俘获重放永远「新鲜」

- **文档与位置**:01 篇 §3.1(信封无新鲜性字段)、§2 P5、§6 R1/R2、§9(离线收件箱暂存);02 篇 §10(威胁模型仅有「enrollment token 重放」行,无消息重放行)。
- **问题**:全链路至少一次投递(P4/R1)意味着信封必然被多方持久持有——网关收件箱为离线节点暂存完整信封(01 §9),任何持有者(被攻陷的团队内节点、被攻陷或作恶的网关)都可原样重放旧信封。重放消息能通过现行全部防线:签名真实(原发送者所签)、A1/A5 团队比对一致、key_epoch 缓存命中(见 SEC-4)、能力检查通过。唯一防线是接收端 `(task_id, attempt, type)` 去重,但其状态保留期在 R1 中无定义——状态清理后,重放的 `task.offer` 与首次投递不可区分,导致任务二次执行;重放的 `task.result` 可污染已归档任务。更糟的是 P5 规定相对时长、`ts` 仅诊断:`offer_ttl_ms` 在接收时刻才换算,被重放的信封在接收方看来永远是新的,连「过期兜底」也不存在。enrollment token 已有单次使用 + TTL,说明作者意识到重放问题,却只覆盖了 token 一处。此字段属信封级决策:P1 的立论就是「事后补鉴权字段是著名痛苦工程」,重放防护缺席 v1,后续补即为自我否定式返工。
- **修改建议**:
  1. 信封 v1 增加新鲜性字段,二选一:(a) `exp`(发送方按本地时钟将相对时限换算的绝对过期时刻),接收方按「接收时刻 ≤ exp + 漂移容忍窗(建议 5–10 分钟)」判废弃;在 P5 中为 `exp` 显式豁免并写明漂移预算,`ts` 保持纯诊断;(b) 每 `from.node_id` 单调递增 `seq`,接收方拒绝回退序号。推荐 (a),实现与审计成本最低。
  2. R1 补去重状态保留期下限:≥ `max(offer_ttl, lease) × max_attempts + drain_ms`,并要求实现方以测试用例覆盖「状态清理后收到旧信封」场景。
  3. 02 §10 增加两行:「消息重放(含网关/收件箱持有者重放)」与「网关作恶(选择性丢弃/延迟/重排/重放注入/元数据画像/吊销抑制)」,分别给出缓解与残余风险。

### SEC-2 · major · A1 不锚定显式 `to.team_id`,跨队消息可穿透网关,「零可达」不成立

- **文档与位置**:02 篇 §7 A1、A0、A5;01 篇 §9(离线暂存路径)。
- **问题**:A1 规则为「`from.team_id ≠ to.team_id` → 拒绝路由;`to.team_id` 缺省时由目录反查」。反向读之:**`to.team_id` 显式填写时,网关按自报值比对,不回源目录**。from 侧已被 A0 钉扎到目录归属,但 to 侧没有。于是跨队路径成立:攻击队 t-x 成员发送 `to: {node_id: 受害节点, team_id: t-x}`——A1 两值相等放行,网关按 `to.node_id` 把跨队消息送达受害节点。讽刺的是,`to.team_id` 留空的诚实写法反而会被正确拒绝。02 §7「跨 team = 零可达,且两条路径都闭合」的论断因此不成立:网关边界已被穿透,仅靠节点侧 A5 兜底;且该跨队消息按 01 §9 会进入受害节点收件箱暂存,受害者上线即收到。
- **修改建议**:
  1. A1 改为恒以目录为锚:`to_team := 目录反查(to.node_id).team_id`(可缓存,失败关闭,守 P12);信封自报 `to.team_id` 仅作一致性核对,与目录不符 → 拒绝路由 + 审计告警(作为伪造信号)。
  2. 补一条明确测试用例:「to.team_id 伪造(与 to.node_id 的目录归属不符)必须被网关拒绝」。
  3. 同理,节点回信(reject/answer)的 `to` 也必须按发起方目录归属锚定,防止回程同样被填票绕过。

### SEC-3 · major · 「不回声」与 R6/§8/A5 的回声边界未定义,跨队伪造消息触发 reject 形成探测 oracle

- **文档与位置**:01 篇 §3.3.4(静默丢弃)、§4.1、§8(未知 type 回 `reject(unsupported_version)`)、§6 R6;02 篇 §7 A5;03 篇 §6 闸 2。
- **问题**:01 §3.3.4 立了「不给探测者任何回声」的原则,但三处机制重新引入回声且边界未定义。尤其矛盾的是:A4 对验签失败静默,而签名合法但跨队的消息(A5 场景,结合 SEC-2 可达)却得到 `reject(policy_denied)` 回声——攻击者的签名本就合法,于是获得对他队节点「存在性/活跃性」的探测通道,与静默原则直接冲突。另外 §8 的版本回执未说明其在验证流水线中的位置:若排在验签之前,未认证探测者可借 unknown type 榨取节点版本信息。全文还缺失一个基础检查:`to.node_id ≠ 本机` 的信封应如何处置(它同时是网关误投/作恶投递的最后防线)。
- **修改建议**:在 01 §3.3/§8 与 03 §6 统一规定回声分级并固定检查顺序:
  1. **静默丢弃 + 审计**:验签失败;`to.node_id ≠ 本机`;跨队(from 钉扎后与本地 team 不同)。
  2. **R6 reject**:验签通过且同 team 的一切拒绝(本地策略、能力、负载、`stale_attempt` 等)。
  3. `unsupported_version`/未知 type 的回执必须排在「验签 + 同 team 复核」之后;若担心版本漂移不可见,明确「仅对已认证同 team 消息回执」的取舍。
  4. 同步修订 03 §6 闸 2:把「team 复核失败」与「本地策略拒绝」拆开——前者静默丢弃,后者保留 `policy_denied` 回执。

### SEC-4 · major · 旧纪元签名无限期有效:验签只做缓存命中,不校验 key_epoch 现势性

- **文档与位置**:01 篇 §3.3.2(公钥按 `(node_id, key_epoch)` 查询、本地缓存);02 篇 §6.2、§10「密钥泄露/被吊销节点」行。
- **问题**:02 §6.2 只规定了缓存未命中与负缓存,未规定「命中的旧纪元正缓存」如何失效。推论:验证方对 `(node, epoch=3)` 的正缓存没有过期与回源复核机制,节点轮换到 epoch 4 甚至被吊销后,**凡持有 epoch 3 缓存的验证方仍无限期接受 epoch 3 签名**。02 §10「密钥泄露 | 轮换 + epoch 失效旧钥」的缓解因此不成立——「epoch 失效旧钥」的前提是验证方校验纪元现势性,而规则里没有这条。被吊销节点在网关路径被 A2 拦截,但 01 §9 的 v1.5 局域网直连路径完全绕开网关,届时节点侧只剩负缓存一道防线,而负缓存只在「未命中/已查到 revoked」时才生效,救不了「命中旧正缓存」的场景。
- **修改建议**:
  1. 02 §6.2 验签判据改为:「缓存命中**且**该 `key_epoch` == 注册中心当前纪元」才通过;纪元不匹配(含比当前旧)→ 回源复核;正缓存必须带 TTL 或随吊销/暂停事件失效。
  2. 明确 v1.5 直连路径下吊销/暂停的收敛承诺(如「节点侧 ≤ 负缓存 TTL」),并把「吊销后旧纪元签名在验证方的存活窗口」写入 02 §10 残余风险列。
  3. 措辞:02 §6.2「拒签」疑为「拒绝该消息/验签不通过」之误——验证方不签名。

### SEC-5 · major · install 管道供应链与开放注册滥用未入威胁模型

- **文档与位置**:纪要 §4/§8.5;02 篇 §4.1–§4.3、§9、§10。
- **问题**:威胁模型没有「安装/分发通道」与「注册滥用」行。`curl …/install.sh | sh -s -- --enroll <token>`(02 §4.1)意味着:(a) 新节点在安装时点无条件执行中心下发的任意代码,中心/CDN 被攻陷或域名劫持 = 在每台新节点植入后门,而**节点身份私钥恰在该时点生成**——TOFU 信任根在此一刻定型,后续所有节点间签名真实性随之沦陷;(b) token 出现在 shell 命令行:进入 shell history(bash/zsh 历史文件、主机镜像/备份),并短暂暴露于 `ps`;5 分钟 TTL 缩小但不消除窗口;(c) 反方向,开放注册(纪要 D5、02 §4.2 未登录路径)无任何限流、配额或成本机制:任何人可脚本化海量 enroll,制造无限单机 team 与节点记录,占用注册中心存储、网关连接与收件箱资源——注册中心是有状态单点(02 §12.4),这是廉价的 DoS 面。
- **修改建议**:
  1. 02 §10 增行:「install/分发通道被攻陷」与「开放注册滥用(海量注册、垃圾 team/节点堆积)」。
  2. token 传递改为 stdin 或环境变量(如 `--enroll-stdin`),文档明示不要把 token 写进命令行;保留 5 分钟 TTL 与单次使用。
  3. §8.5 安装器验收项加入:发布物签名(如 minisign/sigstore)+ 安装脚本内嵌校验和验证 + 仅 HTTPS/HSTS;文档如实声明「安装时点 = 信任根入口」,并把二进制启动自校验/更新签名链列入演进。
  4. `/v1/enroll` 与 `/install` 加 IP/ASN 级限流;未登录路径可加 PoW 或邮箱验证;注册中心对每 owner 节点数、每 IP 注册速率设配额;对长期未认领、长期离线的单机 team/节点定义 GC(自动 revoked + 档案清理)。

### SEC-6 · major · TOFU 定性失真:实际信任锚是注册中心目录,而非 ssh 式首连钉扎

- **文档与位置**:01 篇 §3.3.2;02 篇 §10 TOFU 行、§12.3。
- **问题**:02 §10 把 TOFU 定性为「与 ssh 首连同级」,残余风险只写「首连即被劫持的场景」。实际机制并非 ssh 式:ssh 在客户端钉扎 host key 并在变更时大声告警;群龙的验证方按 `(node_id, key_epoch)` **每次缓存未命中都回源目录**(01 §3.3.2),即注册中心是事实上的 CA,对「哪个节点持哪把钥」拥有不受监督的终局权威。后果:注册中心(或目录写路径)被攻陷,可静默替换全网任意节点的公钥,持续伪造任意节点间消息——这不是「首连窗口」,是信任锚全生命周期风险。且密钥轮换在本系统中是常态操作,「密钥变了」不构成任何告警信号,替换毫无摩擦。§12.3 承认了固化问题,但把问题窄化为「首次 enroll 时背书」,未覆盖运行期权威问题。
- **修改建议**:
  1. 改写 02 §10 TOFU 行定性:「注册中心 = 事实 CA;目录被攻陷 ⇒ 节点间认证整体失守」,与「中心被攻陷」行对齐。
  2. v1 最小硬化:验证方对首次取得的 `(node_id → pubkey)` 做本地永久钉扎;此后发现目录返回的公钥与钉扎不符(且非本节点自己发起的轮换),本地显著告警并要求人工确认后才更新。成本仅为一张本地表 + 一条告警路径。
  3. §12.3 升级为有时间表的承诺:证书链或 key transparency 风格的日志列入路线图,并写明 v1 过渡期对注册中心的信任假设。

### SEC-7 · major · `payload_ref` 已锁结构但无解析安全基线(SSRF/任意 scheme/内网元数据)

- **文档与位置**:01 篇 §4.2(`payload_ref` 字段)、§6 R10;03 篇 §3.1(`net:` 类标签)、§6.1。
- **问题**:R10 把引用结构钉死(`{ref_uri?, repo?, path?, sha256, size}`),解析安全基线完全留白——选型留 §8.4 可以,结构已定则约束必须同步定。攻击面:同队节点或被注入的任务书(03 §6.1 已承认提示注入是「常规路径的固有属性」)可指定任意 `ref_uri`,执行方拉取时构成经典 SSRF——尤其部分节点自带 `net:office-vpn` 这类内网位置,一条 `ref_uri` 指向 `http://169.254.169.254/…` 或内网管理面,就能借执行方之手探测/拖取内网。03 §6.1 的「受限网络出口」只针对任务执行面,未声明覆盖 payload 拉取行为本身;sha256 校验(R10)只防篡改,不防拉取动作本身。
- **修改建议**:在 01 §6 R10 增补解析安全基线(§8.4 选型继承):scheme 白名单(初始仅 https 与系统 git);默认禁止环回、link-local(169.254.0.0/16 等)与私有网段目标,例外须节点策略显式白名单;下载前按 `size` 上限预检,超限拒绝不预取;重定向不得越出白名单;明确 payload 拉取划入远端执行档案的网络出口约束内(03 §6.1 加一句)。

### SEC-8 · major · 同队全互信的模型前提已如实声明,但 v1 缺少零成本缓冲带

- **文档与位置**:02 篇 §7(同 team 全互信)、§10「团队内成员机器被攻陷 | 无」;03 篇 §6.1。
- **问题**:02 §10 诚实声明团队内攻陷「无缓解」,这是对消息面模型前提的正确陈述;但不应据此推迟执行面/运营面上三件便宜事:(a) 无同队 per-source 速率上限——被攻陷节点可向队友无限发射 offer/rpc,耗尽收件箱与执行资源(01 §12.6 的收件箱配额是存侧,不含消息面速率);(b) 远端任务无执行可见性——03 §6.1 只对「敏感操作」要求本地人确认,普通远端任务默认静默执行,用户对「我的机器正在为谁干活」无感知;(c) 无即时总闸——`accepting`(03 §3.3)是 60s 快照字段,翻转依赖周期/事件上报,不是即时停摆开关。
- **修改建议**:v1 增补最小缓解集(均不改信封、不破坏 P7):节点本地对同队来源的 offer/rpc 设速率上限(超限 `reject(busy, retry_after_ms)`);任意远端任务开始/结束时本地可见通知(通知不阻断);提供本地即时生效的「暂停接远端单」开关(语义独立于动态档案刷新)。

### SEC-9 · minor · 凭证恢复三场景的组合缺口与 suspend 语义盲区

- **文档与位置**:02 篇 §6.1、§4.2、§5.2(状态机);01 篇 §9(v1.5 直连)。
- **问题**:(a) **token 与私钥同时不可用**(磁盘损坏、误清理)只能走「设备丢失」路径:重装 + 新 node_id——身份更替导致 trace 连续性断裂、牵头方本地记忆失配、需 owner 手工清理旧节点,文档未陈述这一运维代价;(b) 「常规轮换」要求 token 与当前私钥双因子,任一单独失效即无法轮换,同样坠落为重装路径——该设计防 token 窃取者换钥(合理取舍),但代价未写明;(c) `qlong join` 以旧凭证认证,凭证受损节点无法自助认领,只能重装;(d) `suspended` 不吊销密钥:网关路径被 A2 拦住,但 v1.5 直连路径下被窃设备在团队内网仍能通过 A4/A5——「suspend ≠ 密钥失效」未被声明。
- **修改建议**:§6.1 补「凭证全失/仅 token 失效」一行,明确「换身份 = 新 node_id」的运维后果与 trace 断裂说明;在 §6.1 注明 suspend 语义边界,并联动 SEC-4:验证方对非 active 节点的纪元应回源拒绝。

### SEC-10 · minor · 能力档案隐私:缺中心侧留存/删除语义与标签敏感度分级

- **文档与位置**:03 篇 §8、§4;02 篇 §5.2(`caps_rev`)、§9。

## 亮点

1. **A0 from 钉扎是评审修订的正确产物**:识别「ACL 全部比对自报字段」这一类根本漏洞,并给出对诚实发送者无感的修法;同一轮把 rpc.* 补入必签(01 §3.1/§4.1 与 02 A4 现已一致,01 §12 开放问题 5 亦被 03 §6 关闭),文档间接口咬合良好,显示了可迭代的威胁建模过程。
2. **双重身份/双重执法分层清晰(P9/P10)**:node token(通行证,可随时吊销重发)与 Ed25519 密钥(身份,轮换有纪元)职责分离、失效后果分开处理;网关主执法 + 节点复核 + P12 失败关闭,单点失守有兜底。
3. **03 §6.1 远端任务执行档案是全文最成熟的安全设计**:正面承认提示注入为「常规路径的固有属性」而非边缘攻击;五维默认降权,加上「offer 可声明 `requires` 但永远不能放宽档案」的不变式,把权限收窄权正确放在执行方。
4. **威胁模型带残余风险列且如实声明模型前提**(团队内攻陷无解、`enc` 启用前中心可读 body),不假装安全——设计文档中少见的质量。
